# ScalarDB 3.16 Release Notes

This page includes a list of release notes for ScalarDB 3.16.

## v3.16.9

**Release date:** November 11, 2026

### Summary

This release lets you repair the coordinator tables and replication tables with Schema Loader without a schema file. It also fixes issues with conditional puts and table import in JDBC databases, data correctness issues involving BLOB values in ScalarDB Cluster and ScalarDB SQL, and SQL parsing issues in ScalarDB SQL. Additionally, this release strengthens security through dependency upgrades and vulnerability fixes.

### Community edition

#### Improvements

- Made the schema file optional for `--repair-all` in Schema Loader when `--coordinator` or `--replication-tables` is specified, so that you can repair the coordinator tables and replication tables without re-applying table schemas. In addition, running `--repair-all` without a schema file, `--coordinator`, or `--replication-tables` now does nothing and exits successfully instead of failing with an error. ([#4183](https://github.com/scalar-labs/scalardb/pull/4183))

#### Bug fixes

- Fixed an issue where a conditional put (`PutIfExists` or `PutIf`) that specifies only primary key values failed with an SQL error in JDBC databases. In Spanner, such a put still fails for tables that have only primary key columns. ([#4129](https://github.com/scalar-labs/scalardb/pull/4129))
- Fixed [CVE-2026-91403](https://github.com/advisories/GHSA-9h75-rf66-wh3r "CVE-2026-91403") and [CVE-2026-114820](https://github.com/advisories/GHSA-255q-pwv4-fjj7 "CVE-2026-114820") (eMudhra CA compromise) in the ScalarDB Schema Loader and ScalarDB Data Loader CLI container images by updating the base image to Eclipse Temurin 21.0.13_9, which no longer trusts the compromised emSign root CAs. ([#4143](https://github.com/scalar-labs/scalardb/pull/4143))
- Upgraded the Guava library to fix a security issue: [CVE-2026-102554](https://github.com/advisories/GHSA-xxph-c9ww-hj94 "CVE-2026-102554") ([#4144](https://github.com/scalar-labs/scalardb/pull/4144))
- Applications that use ScalarDB as a library now get the fixed Netty and Jackson versions, unless they manage those versions themselves. Previously, fixes for vulnerabilities in these libraries (for example, [CVE-2026-75595](https://github.com/advisories/GHSA-c4c3-7fpv-j4q5 "CVE-2026-75595") in Netty and [CVE-2026-89407](https://github.com/advisories/GHSA-p6pp-m3f8-5c89 "CVE-2026-89407"), [CVE-2026-89425](https://github.com/advisories/GHSA-7hhh-6rmp-j9qf "CVE-2026-89425"), [CVE-2026-68497](https://github.com/advisories/GHSA-q4xh-88c3-wmh7 "CVE-2026-68497"), [CVE-2026-91776](https://github.com/advisories/GHSA-wv8q-qhhj-9h54 "CVE-2026-91776"), and [CVE-2026-91777](https://github.com/advisories/GHSA-cxp5-3px4-pw24 "CVE-2026-91777") in Jackson) applied only to ScalarDB's own builds and container images. As a result, Jackson in those applications is upgraded to 2.22. Depending on the ScalarDB version, applications built with Maven previously got much older versions, such as `jackson-databind` 2.7 and Netty 4.1.94. This release also fixes [CVE-2026-73508](https://github.com/advisories/GHSA-mfg7-5gfp-c4w3 "CVE-2026-73508") in Netty, which affected the Schema Loader and Data Loader CLI images as well as those applications. ([#4146](https://github.com/scalar-labs/scalardb/pull/4146))
- Fixed an issue where importing a table from Oracle, MySQL, MariaDB, or TiDB registered the primary key columns in the alphabetical order of the column names instead of the order of the table's primary key. For tables imported after this fix, specify keys, including `--partition-key` for Data Loader exports, in the order of the table's primary key. Tables imported before this fix keep their existing order. ([#4175](https://github.com/scalar-labs/scalardb/pull/4175))
- Upgraded Micrometer (`micrometer-core`, `micrometer-observation`, and `micrometer-commons`) to 1.15.12 to fix [CVE-2026-40983](https://github.com/advisories/GHSA-w737-wx49-qj23 "CVE-2026-40983") and [CVE-2026-40984](https://github.com/advisories/GHSA-g3pr-3p32-fp23 "CVE-2026-40984"). ScalarDB now declares them directly and excludes them from the libraries that bring them in, so applications that use ScalarDB as a library also get the fixed version, unless they manage the Micrometer version themselves. ([#4192](https://github.com/scalar-labs/scalardb/pull/4192))

### Enterprise edition

#### Bug fixes

##### ScalarDB Cluster

- Fixed [CVE-2026-91403](https://github.com/advisories/GHSA-9h75-rf66-wh3r "CVE-2026-91403") and [CVE-2026-114820](https://github.com/advisories/GHSA-255q-pwv4-fjj7 "CVE-2026-114820") (eMudhra CA compromise) in all ScalarDB Cluster container images by updating the base images to Eclipse Temurin 21.0.13_9 and, for the UBI-based node image, `java-21-openjdk` 21.0.13.0.9, which no longer trust the compromised emSign root CAs.
- Upgraded the grpc_health_probe binary to fix a security issue: [CVE-2026-116587](https://github.com/advisories/GHSA-mgcc-cww5-fp2q "CVE-2026-116587")
- Upgraded the Guava library to fix a security issue: [CVE-2026-102554](https://github.com/advisories/GHSA-xxph-c9ww-hj94 "CVE-2026-102554")
- Fixed a bug where the ScalarDB Cluster client read a BLOB value bound as a `ByteBuffer` to the end of the buffer each time it sent the value, so the value was sent as an empty BLOB from the second time on, such as when a statement was executed again or retried, when the same buffer was bound to more than one bind marker, or when statements in a batch shared the same value. As a result, an empty BLOB could be written, or BLOB columns could be compared with an empty BLOB, without any error. The client now copies the bytes without changing the buffer's position. This fix does not repair data that was already affected.
- Upgraded Bouncy Castle (`bcprov-jdk18on`, `bcpkix-jdk18on`, and `bcutil-jdk18on`) to 1.86 in the Java client SDK and the embedding Java client SDK to fix [CVE-2025-14813](https://github.com/advisories/GHSA-574f-3g2m-x479 "CVE-2025-14813"), [CVE-2026-0636](https://github.com/advisories/GHSA-c3fc-8qff-9hwx "CVE-2026-0636"), [CVE-2026-5588](https://github.com/advisories/GHSA-wg6q-6289-32hp "CVE-2026-5588"), [CVE-2026-5598](https://github.com/advisories/GHSA-p93r-85wp-75v3 "CVE-2026-5598"), [CVE-2026-8763](https://github.com/advisories/GHSA-9pwp-9qqc-pr26 "CVE-2026-8763"), and [CVE-2026-13506](https://github.com/advisories/GHSA-qp49-qgx5-5m26 "CVE-2026-13506"). Applications that use these SDKs now get the fixed version, unless they manage the Bouncy Castle version themselves. Previously, the fixed version applied only to ScalarDB Cluster's own builds and container images other than the BYOL ones, which loaded Bouncy Castle 1.70 classes that a dependency brought in. The BYOL container images now use the fixed version, too.
- Applications that use the Java client SDK or the embedding Java client SDK and build with Maven now get the same version for all Jackson artifacts. Previously, some of them, such as `jackson-dataformat-cbor`, could be at older versions that other dependencies of the SDKs request. The embedding Java client SDK no longer exposes Jackson as a compile-time dependency. If your application uses Jackson directly and relied on the SDK to provide it, declare Jackson in your application's build.

##### ScalarDB GraphQL

- Upgraded the Guava library to fix a security issue: [CVE-2026-102554](https://github.com/advisories/GHSA-xxph-c9ww-hj94 "CVE-2026-102554")

##### ScalarDB SQL

- Upgraded the Guava library to fix a security issue: [CVE-2026-102554](https://github.com/advisories/GHSA-xxph-c9ww-hj94 "CVE-2026-102554")
- Fixed `Value.hashCode()` for BLOB values created from `byte[]` so that it is consistent with `equals()`. This inconsistency could cause a `SELECT`, `UPDATE`, or `DELETE` statement that repeats the same BLOB equality condition on a primary-key or indexed column in every `OR` group to be planned with a less efficient scan, or as a cross-partition scan that fails unless cross-partition scan filtering is enabled.
- Fixed two bugs that could silently write or compare wrong BLOB values. In direct mode, a BLOB value bound as a `ByteBuffer` through `BoundStatement.setBlob()`, `Value.ofBlob()`, `Value.of()`, or the JDBC `setObject()` method was read to the end of the buffer each time it was used, so an `UPDATE` statement that updated multiple rows, or a statement executed again, wrote an empty BLOB or compared BLOB columns with an empty BLOB. In the JDBC driver, `setBytes()` and `setObject()` kept a reference to the application's array or buffer, so reusing one array or buffer for each row of a batch wrote the last contents to every row. ScalarDB SQL now copies these values instead of reading the application's buffer or array when it uses them. This fix does not repair data that was already affected.
- Fixed a bug where the SQL parser misread some SQL. It dropped characters that it could not read, so `INSERT INTO ns.té` was executed on the table `ns.t`, and names quoted with backticks or square brackets were accepted. It also read a number followed by a word without a space, such as `5AND`, as a number and a word, and ignored a block comment that was not terminated together with the rest of the statement. In ScalarDB Cluster, such SQL could make a statement outside a transaction run with the credentials in the client configuration instead of those in its `WITH` clause. Such SQL is now rejected with a syntax error, and `--` now starts a line comment whatever follows it, as in the SQL standard. The comment `/*!*/` no longer makes the parser skip the SQL up to the next `*/`, which could make a `DELETE` statement delete all the rows.

## v3.16.8

**Release date:** October 30, 2026

### Summary

This release adds support for SQL Server 2025 and drops support for SQL Server 2017. It also improves transaction reliability and error handling in Consensus Commit, fixes various issues in storage adapters, and enhances resource management. Additionally, this release strengthens security through authentication and authorization fixes, dependency upgrades, and vulnerability mitigations.

### Community edition

#### Improvements

- Fixed an issue where a conflict error, such as a lock wait timeout or a serialization failure, in a single put or delete operation on JDBC databases was not classified as retriable. As a result, Consensus Commit can now report such a conflict during commit as `CommitConflictException` instead of `CommitException` or `UnknownTransactionStatusException`. ([#3852](https://github.com/scalar-labs/scalardb/pull/3852))
- Fixed the Consensus Commit record recovery to retry conflict errors reported by the underlying storage, and to report a conflict that persists as a conflict so that the transaction can be retried. ([#3853](https://github.com/scalar-labs/scalardb/pull/3853))
- Added support for SQL Server 2025 and dropped support for SQL Server 2017. ([#3998](https://github.com/scalar-labs/scalardb/pull/3998))
- Changed table import to reject column types that can't follow the TEXT collation order: SQL Server `nchar`, `nvarchar`, `text`, and `ntext`; Oracle `NCHAR` and `NVARCHAR2`; and Db2 `GRAPHIC`, `VARGRAPHIC`, and `DBCLOB`. ([#4051](https://github.com/scalar-labs/scalardb/pull/4051))
- Upgraded the SQL Server JDBC driver to 13.6.0 and fixed TIMESTAMPTZ values dated before October 15, 1582, being stored up to 10 days off in SQL Server. TIMESTAMPTZ values dated before October 15, 1582, that were stored in SQL Server by a previous ScalarDB version are read back up to 10 days earlier than the value that was written. If you have such data, consider migrating it to remove the offset. ([#3971](https://github.com/scalar-labs/scalardb/pull/3971))
- Mitigate [CVE-2026-91403](https://github.com/advisories/GHSA-9h75-rf66-wh3r "CVE-2026-91403") and [CVE-2026-114820](https://github.com/advisories/GHSA-255q-pwv4-fjj7 "CVE-2026-114820") (eMudhra CA compromise) by removing the affected emSign root CAs from the cacerts of all container images, and update the base image of the ScalarDB Schema Loader and ScalarDB Data Loader CLI container images from Java 8 (Eclipse Temurin 8) to Java 21 (Eclipse Temurin 21). The images set no JVM options by default, so this affects only users who pass Java 8-specific JVM options (for example, `-XX:+PrintGCDateStamps` through `JAVA_TOOL_OPTIONS`), which now make the JVM fail to start. ([#4112](https://github.com/scalar-labs/scalardb/pull/4112))

#### Bug fixes

- Fixed an issue where rolling back a Consensus Commit transaction with an open scanner, including the automatic rollback of an expired or evicted transaction, could fail with an IllegalArgumentException and leave the remaining scanners open and the group commit slot unreleased. ([#3867](https://github.com/scalar-labs/scalardb/pull/3867))
- Fixed the Cassandra adapter so that an update applied by a conditional write is no longer silently discarded when it runs in the same millisecond as a preceding non-conditional write to the same record. The adapter now takes write timestamps from the server and sends every request for a partition to the same replica. ([#3890](https://github.com/scalar-labs/scalardb/pull/3890))
- Fixed an issue where Consensus Commit accepted invalid conditions on conditional mutations instead of rejecting them. ([#3871](https://github.com/scalar-labs/scalardb/pull/3871))
- Fixed an issue in DynamoDB where a single conditional write that the AWS SDK retried could be reported as not applied, even though the write had been applied. Such a write is now reported as having an unknown outcome. Also fixed an issue where some failures in DynamoDB operations were thrown as unchecked AWS SDK exceptions instead of `ExecutionException`. ([#3922](https://github.com/scalar-labs/scalardb/pull/3922))
- Fixed an issue where a scan condition with the `!=`, `<`, or `<=` operator was satisfied by a NULL column value in Cassandra, Cosmos DB, DynamoDB, and Object Storage. Also fixed an issue where a `!=` condition was satisfied by a NULL column value in `PutIf` or `DeleteIf` in Cassandra, DynamoDB, and Consensus Commit, and in `UpdateIf` in Consensus Commit. ([#3930](https://github.com/scalar-labs/scalardb/pull/3930))
- Fixed an issue where `repairTable()` on DynamoDB did not enable auto-scaling for existing global secondary indexes, for example after `createTable()` or `createIndex()` failed before enabling auto-scaling (such as when Application Auto Scaling permissions were missing). `repairTable()` now also keeps the existing auto-scaling range of a table instead of resetting it to the given or default request unit, so running repair without `--ru` no longer lowers the capacity of existing tables, including the Coordinator table. To change the auto-scaling range of an existing table, use the AWS console or CLI. If `createTable()` or `createIndex()` with auto-scaling enabled failed before, run `repairTable()` again after upgrading, with the schema that includes the index and the same request unit as at creation. If `repairTable()` (or Schema Loader with `--repair-all`) was run before without `--ru` or with a smaller request unit, check the auto-scaling range of existing tables, including the Coordinator table, and restore it with the AWS console or CLI, because `repairTable()` no longer changes the range of existing tables. ([#3949](https://github.com/scalar-labs/scalardb/pull/3949))
- Changed the error code for dropping a namespace that contains non-ScalarDB tables from `DB-CORE-10216` to `DB-CORE-10249` so that it matches the error code in other versions. ([#3955](https://github.com/scalar-labs/scalardb/pull/3955))
- Fixed an issue where a scanner opened outside a transaction was never closed if a client abandoned it while active transaction management kept it across requests. Such a scanner kept its transaction and storage resources, for example, a database connection and an open database transaction. Now, such a scanner is closed when it has not been used for the active transaction expiration time, or when more such scanners than the maximum number of active transactions are open. ([#3992](https://github.com/scalar-labs/scalardb/pull/3992))
- Upgraded the Netty and Jackson libraries to fix security issues: [CVE-2026-75595](https://github.com/advisories/GHSA-c4c3-7fpv-j4q5 "CVE-2026-75595"), [CVE-2026-89407](https://github.com/advisories/GHSA-p6pp-m3f8-5c89 "CVE-2026-89407"), [CVE-2026-89425](https://github.com/advisories/GHSA-7hhh-6rmp-j9qf "CVE-2026-89425"), [CVE-2026-68497](https://github.com/advisories/GHSA-q4xh-88c3-wmh7 "CVE-2026-68497"), [CVE-2026-91776](https://github.com/advisories/GHSA-wv8q-qhhj-9h54 "CVE-2026-91776"), and [CVE-2026-91777](https://github.com/advisories/GHSA-cxp5-3px4-pw24 "CVE-2026-91777") ([#3996](https://github.com/scalar-labs/scalardb/pull/3996))

### Enterprise edition

#### Bug fixes

##### ScalarDB Cluster

- Fixed an issue where, with authentication enabled, a client could keep reading from an open scanner after its auth token had expired or been revoked, or after its READ privilege had been revoked. Fetching from a scanner now re-checks the READ privilege. For OIDC clients, a JWT that expires during a scan now causes an authentication error at the next fetch, as with get and scan; a client that supplies the JWT through `OidcJwtAccessTokenHolder` can set a fresh JWT and continue the scan.
- Upgraded the Jackson, Netty, and Bouncy Castle libraries to fix security issues: [CVE-2026-8763](https://github.com/advisories/GHSA-9pwp-9qqc-pr26 "CVE-2026-8763"), [CVE-2026-13506](https://github.com/advisories/GHSA-qp49-qgx5-5m26 "CVE-2026-13506"), [CVE-2026-68497](https://github.com/advisories/GHSA-q4xh-88c3-wmh7 "CVE-2026-68497"), [CVE-2026-75595](https://github.com/advisories/GHSA-c4c3-7fpv-j4q5 "CVE-2026-75595"), [CVE-2026-89407](https://github.com/advisories/GHSA-p6pp-m3f8-5c89 "CVE-2026-89407"), [CVE-2026-89425](https://github.com/advisories/GHSA-7hhh-6rmp-j9qf "CVE-2026-89425"), [CVE-2026-91776](https://github.com/advisories/GHSA-wv8q-qhhj-9h54 "CVE-2026-91776"), and [CVE-2026-91777](https://github.com/advisories/GHSA-cxp5-3px4-pw24 "CVE-2026-91777")
- Upgraded the grpc_health_probe binary to fix security issues: [CVE-2026-56851](https://github.com/advisories/GHSA-gx9w-9qq8-m485 "CVE-2026-56851"), [CVE-2026-78667](https://github.com/advisories/GHSA-f4xw-m386-m277 "CVE-2026-78667"), CVE-2026-78669, [CVE-2026-84304](https://github.com/advisories/GHSA-vp52-pcj8-j9qc "CVE-2026-84304"), [CVE-2026-84445](https://github.com/advisories/GHSA-2v4p-qf9q-27wj "CVE-2026-84445"), and [CVE-2026-97031](https://github.com/advisories/GHSA-hq7w-2xrq-wp2j "CVE-2026-97031")
- Fixed an issue where closing a ScalarDB Cluster client in the `direct-kubernetes` client mode left behind a thread and a connection to the Kubernetes API server. An application that repeatedly created and closed clients, including through the ScalarDB SQL JDBC driver, could eventually fail to create new threads.
- Mitigate [CVE-2026-91403](https://github.com/advisories/GHSA-9h75-rf66-wh3r "CVE-2026-91403") and [CVE-2026-114820](https://github.com/advisories/GHSA-255q-pwv4-fjj7 "CVE-2026-114820") (eMudhra CA compromise) by removing the affected emSign root CAs from the cacerts of all container images

## v3.16.6

**Release date:** August 2, 2026

### Summary

This release updates the deprecation policy, improves `repairTable` behavior, fixes Consensus Commit, Cluster rollback/pause, and SQL metadata cache issues, and upgrades several dependencies to address security vulnerabilities across the Community and Enterprise editions.

### Community edition

#### Improvements

- Changed the deprecation policy so that APIs and configurations marked as deprecated will now be removed in 4.0.0 instead of 5.0.0. ([#3520](https://github.com/scalar-labs/scalardb/pull/3520))
- Improved `repairTable` to skip rewriting a table's metadata when it is already up to date (and, for Cosmos DB, to skip updating the container indexing policy when it already matches), avoiding unnecessary writes. ([#3613](https://github.com/scalar-labs/scalardb/pull/3613))

#### Bug fixes

- Fixed an issue in Consensus Commit where a `Get` operation using a secondary index could fail with an `IllegalArgumentException` when another record with the same indexed value was concurrently being deleted and inserted. ([#3607](https://github.com/scalar-labs/scalardb/pull/3607))
- Fixed an issue in Consensus Commit where a read-only transaction could fail when coordinator write omission on read-only was disabled and coordinator group commit was enabled. ([#3614](https://github.com/scalar-labs/scalardb/pull/3614))
- Fixed a bug where aborting an in-flight, group-committed transaction by ID via `DistributedTransactionManager.rollback(String)` / `abort(String)` could be lost when the Coordinator group commit feature was enabled. ([#3619](https://github.com/scalar-labs/scalardb/pull/3619))

## v3.16.5

**Release date:** April 15, 2026

### Summary

This release includes improvements and bug fixes.

:::warning Backward-incompatible changes

- **Existing tables require `repairTable()` to create the new before-image secondary index.** Index-based `Get`, `Scan`, and `ScanAll` in Consensus Commit now rely on a companion `before_<col>` index. Until you run `repairTable()` on each existing table, ScalarDB logs a warning at startup and index-based reads fall back to the previous behavior, which may miss records whose indexed column is being concurrently updated. The configuration `scalar.db.consensus_commit.index.eventually_consistent_read.enabled` is provided as an opt-out but is not recommended for new workloads.
- **MySQL Connector/J replaced with MariaDB Connector/J.** SSL is no longer enabled by default. If you connect to MySQL 8.0 or later with `caching_sha2_password` authentication, add `sslMode=REQUIRED` or `allowPublicKeyRetrieval=true` to your JDBC URL. No action is required for `jdbc:mysql://` URLs because ScalarDB automatically appends `permitMysqlScheme` for compatibility.

:::

##### ScalarDB Cluster
