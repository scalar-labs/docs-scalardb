# ScalarDB 3.20 リリースノート

このページには、ScalarDB 3.20 のリリースノートのリストが含まれています。

## v3.20.1

**発売日:** 2026年11月11日

### まとめ

このリリースでは、より多くのデータベースで READ COMMITTED 分離レベルをサポートし、インポートされたテーブルに関する問題を修正することで、トランザクションメタデータの分離を改善しました。また、特に ScalarDB Cluster と ScalarDB SQL における BLOB 値に関連するいくつかのデータ正確性の問題に対処し、SQL の解析と検証を改善しました。さらに、このリリースでは、スキーマ管理を強化し、さまざまなストレージアダプターの問題を修正し、依存関係のアップグレードと脆弱性の修正によってセキュリティを強化しました。

### Community edition

#### 改善点

- ScalarDB が一貫した仮想テーブルの読み取りに必要とする分離レベルを、Oracle、PostgreSQL、AlloyDB、YugabyteDB、MySQL、MariaDB、TiDB で READ COMMITTED に引き下げました。この変更により、これらのデータベースで、Oracle と PostgreSQL のデフォルトの分離レベルである READ COMMITTED でトランザクションメタデータの分離を使用できるようになり、Oracle で SERIALIZABLE が不要になりました。 ([#4148](https://github.com/scalar-labs/scalardb/pull/4148))
- Schema Loader の `--repair-all` で、`--coordinator` または `--replication-tables` が指定されている場合にスキーマファイルを省略できるようにしました。これにより、テーブルスキーマを再適用せずに、コーディネーターテーブルとレプリケーションテーブルを修復できます。さらに、スキーマファイル、`--coordinator`、`--replication-tables` のいずれも指定せずに `--repair-all` を実行した場合、エラーで失敗する代わりに、何も行わずに正常終了するようになりました。 ([#4183](https://github.com/scalar-labs/scalardb/pull/4183))

#### バグの修正

- JDBC データベースで、主キーの値のみを指定した条件付き put (`PutIfExists` または `PutIf`) が SQL エラーで失敗する問題を修正しました。Spanner では、主キーの列のみを持つテーブルに対するこのような put は引き続き失敗します。 ([#4129](https://github.com/scalar-labs/scalardb/pull/4129))
- JDBC データベースで、トランザクションメタデータの分離を使用してインポートされたテーブルに関する問題を修正しました。インポート以降にどのトランザクションも書き込んでいないレコードが、それを書き込んだトランザクションがロールバックされた後に、更新も削除もできなくなる問題がありました。また、最初のトランザクションがレコードを読み取った後に別のトランザクションが削除したレコードを、最初のトランザクションが再作成できる問題がありました。Spanner では、後者の問題は、主キーの列のみを持つテーブルで引き続き発生します。この問題によってすでに更新も削除もできなくなっているレコードは、アップグレード後もそのままです。これらを復旧するには、すべてのアプリケーションをアップグレードした後、インポートされたテーブルの `<table_name>_tx_metadata` テーブルから、`tx_id` 列が `NULL` のレコードを削除してください。例: `DELETE FROM <namespace>.<table_name>_tx_metadata WHERE tx_id IS NULL`。 ([#4131](https://github.com/scalar-labs/scalardb/pull/4131))
- JDBC データベースで、トランザクションメタデータの分離を使用してインポートされたテーブルにおいて、ワンフェーズコミットが有効な場合に、インポート以降にどのトランザクションも書き込んでいないレコードを削除すると `IllegalArgumentException` で失敗する問題を修正しました。 ([#4133](https://github.com/scalar-labs/scalardb/pull/4133))
- ScalarDB Schema Loader および ScalarDB Data Loader CLI コンテナイメージで、ベースイメージを Eclipse Temurin 21.0.13_9 に更新することにより、[CVE-2026-91403](https://github.com/advisories/GHSA-9h75-rf66-wh3r "CVE-2026-91403") と [CVE-2026-114820](https://github.com/advisories/GHSA-255q-pwv4-fjj7 "CVE-2026-114820") (eMudhra CA の侵害) を修正しました。このベースイメージは、侵害された emSign ルート CA を信頼しなくなりました。 ([#4143](https://github.com/scalar-labs/scalardb/pull/4143))
- [CVE-2026-8763](https://github.com/advisories/GHSA-9pwp-9qqc-pr26 "CVE-2026-8763") と [CVE-2025-14813](https://github.com/advisories/GHSA-574f-3g2m-x479 "CVE-2025-14813") を修正するために、Bouncy Castle (`bcprov-jdk18on`) を 1.86 にアップグレードしました。ScalarDB は Bouncy Castle を直接宣言し、Bouncy Castle を取り込むライブラリからは除外するようになったため、ScalarDB をライブラリとして使用するアプリケーションも、Bouncy Castle のバージョンを自身で管理していない限り、修正済みのバージョンを使用します。 ([#4145](https://github.com/scalar-labs/scalardb/pull/4145))
- ScalarDB をライブラリとして使用するアプリケーションは、Netty と Jackson のバージョンを自身で管理していない限り、修正済みのバージョンを使用するようになりました。これまで、これらのライブラリの脆弱性の修正 (たとえば、Netty の [CVE-2026-75595](https://github.com/advisories/GHSA-c4c3-7fpv-j4q5 "CVE-2026-75595")、Jackson の [CVE-2026-89407](https://github.com/advisories/GHSA-p6pp-m3f8-5c89 "CVE-2026-89407")、[CVE-2026-89425](https://github.com/advisories/GHSA-7hhh-6rmp-j9qf "CVE-2026-89425")、[CVE-2026-68497](https://github.com/advisories/GHSA-q4xh-88c3-wmh7 "CVE-2026-68497")、[CVE-2026-91776](https://github.com/advisories/GHSA-wv8q-qhhj-9h54 "CVE-2026-91776")、[CVE-2026-91777](https://github.com/advisories/GHSA-cxp5-3px4-pw24 "CVE-2026-91777")) は、ScalarDB 自体のビルドとコンテナイメージにのみ適用されていました。その結果、これらのアプリケーションの Jackson は 2.22 にアップグレードされます。ScalarDB のバージョンによっては、Maven でビルドされたアプリケーションは、これまで `jackson-databind` 2.7 や Netty 4.1.94 など、はるかに古いバージョンを使用していました。このリリースでは、これらのアプリケーションだけでなく Schema Loader および Data Loader CLI イメージにも影響していた、Netty の [CVE-2026-73508](https://github.com/advisories/GHSA-mfg7-5gfp-c4w3 "CVE-2026-73508") も修正しました。 ([#4146](https://github.com/scalar-labs/scalardb/pull/4146))
- Amazon S3 を使用する Object Storage アダプターで、複数のテーブルを同時にトランケートまたは削除すると、無期限にハングする可能性がある問題を修正しました。 ([#4149](https://github.com/scalar-labs/scalardb/pull/4149))
- Oracle、MySQL、MariaDB、または TiDB からテーブルをインポートする際に、主キーの列が、テーブルの主キーの順序ではなく列名のアルファベット順で登録される問題を修正しました。この修正後にインポートされたテーブルでは、Data Loader のエクスポート用の `--partition-key` を含め、テーブルの主キーの順序でキーを指定してください。この修正前にインポートされたテーブルは、既存の順序のままです。 ([#4175](https://github.com/scalar-labs/scalardb/pull/4175))
- 部分的なクラスタリングキーを包含的な終了境界として指定したスキャンが、同じトランザクション内で範囲内に書き込まれたレコードを返さずに成功する問題を修正しました。このようなスキャンは、`DB-CORE-10106` で失敗するようになりました。これは、制限またはすべての結果を読み取る前にスキャナーが閉じられたためにレコードが返されなかった場合、書き込みが既存のレコードを更新する場合、およびスキャナーを最後まで読み取った後、閉じる前に範囲内の新しいキーが書き込まれた場合にも適用されます。 ([#4193](https://github.com/scalar-labs/scalardb/pull/4193))
- [CVE-2026-40983](https://github.com/advisories/GHSA-w737-wx49-qj23 "CVE-2026-40983") と [CVE-2026-40984](https://github.com/advisories/GHSA-g3pr-3p32-fp23 "CVE-2026-40984") を修正するために、Micrometer (`micrometer-core`、`micrometer-observation`、`micrometer-commons`) を 1.15.12 にアップグレードしました。ScalarDB はこれらを直接宣言し、これらを取り込むライブラリからは除外するようになったため、ScalarDB をライブラリとして使用するアプリケーションも、Micrometer のバージョンを自身で管理していない限り、修正済みのバージョンを使用します。 ([#4192](https://github.com/scalar-labs/scalardb/pull/4192))

### Enterprise edition

#### バグの修正

##### ScalarDB Cluster

- 埋め込みクライアントが、`ContainsString` などのサポートされていないフィルタータイプに対して、`UnsupportedOperationException` ではなく `AssertionError` をスローする問題を修正しました。
- すべての ScalarDB Cluster コンテナイメージで、ベースイメージを Eclipse Temurin 21.0.13_9 に、UBI ベースのノードイメージでは `java-21-openjdk` 21.0.13.0.9 に更新することにより、[CVE-2026-91403](https://github.com/advisories/GHSA-9h75-rf66-wh3r "CVE-2026-91403") と [CVE-2026-114820](https://github.com/advisories/GHSA-255q-pwv4-fjj7 "CVE-2026-114820") (eMudhra CA の侵害) を修正しました。これらは、侵害された emSign ルート CA を信頼しなくなりました。
- セキュリティ上の問題を修正するために grpc_health_probe バイナリをアップグレードしました: [CVE-2026-116587](https://github.com/advisories/GHSA-mgcc-cww5-fp2q "CVE-2026-116587")
- ScalarDB Cluster クライアントが、`ByteBuffer` としてバインドされた BLOB 値を送信するたびにバッファの末尾まで読み取っていたため、2回目以降 (ステートメントの再実行やリトライ時、同じバッファが複数のバインドマーカーにバインドされている場合、またはバッチ内のステートメントが同じ値を共有している場合など) は、その値が空の BLOB として送信されるバグを修正しました。その結果、エラーなしで空の BLOB が書き込まれたり、BLOB 列が空の BLOB と比較されたりする可能性がありました。クライアントは、バッファの位置を変更せずにバイト列をコピーするようになりました。この修正では、すでに影響を受けたデータは修復されません。
- 書き込みバッファリングが有効な場合に、ScalarDB Cluster クライアントが、バッファリングされた `INSERT` および `UPSERT` ステートメントを、実行時の値ではなく、バッファリングされたステートメントの送信時の値で送信するバグを修正しました。アプリケーションがステートメントの実行後に `BoundStatement` や BLOB 値のバイト配列または `ByteBuffer` を再利用すると、それを使用しているバッファリング済みのすべてのステートメントが最後の値で送信され、エラーなしで誤った値の行が書き込まれる可能性がありました。クライアントは、ステートメントをバッファリングする際にその値をコピーするようになりました。この修正では、すでに影響を受けたデータは修復されません。
- Java クライアント SDK と埋め込み Java クライアント SDK で、[CVE-2025-14813](https://github.com/advisories/GHSA-574f-3g2m-x479 "CVE-2025-14813")、[CVE-2026-0636](https://github.com/advisories/GHSA-c3fc-8qff-9hwx "CVE-2026-0636")、[CVE-2026-5588](https://github.com/advisories/GHSA-wg6q-6289-32hp "CVE-2026-5588")、[CVE-2026-5598](https://github.com/advisories/GHSA-p93r-85wp-75v3 "CVE-2026-5598")、[CVE-2026-8763](https://github.com/advisories/GHSA-9pwp-9qqc-pr26 "CVE-2026-8763")、[CVE-2026-13506](https://github.com/advisories/GHSA-qp49-qgx5-5m26 "CVE-2026-13506") を修正するために、Bouncy Castle (`bcprov-jdk18on`、`bcpkix-jdk18on`、`bcutil-jdk18on`) を 1.86 にアップグレードしました。これらの SDK を使用するアプリケーションは、Bouncy Castle のバージョンを自身で管理していない限り、修正済みのバージョンを使用するようになりました。これまで、修正済みのバージョンは、ScalarDB Cluster 自体のビルドと、BYOL 以外のコンテナイメージにのみ適用されていました。BYOL コンテナイメージでは、依存関係が取り込んだ Bouncy Castle 1.70 のクラスが読み込まれていました。BYOL コンテナイメージも、修正済みのバージョンを使用するようになりました。
- Java クライアント SDK または埋め込み Java クライアント SDK を使用し、Maven でビルドするアプリケーションは、すべての Jackson アーティファクトで同じバージョンを使用するようになりました。これまで、`jackson-dataformat-cbor` など一部のアーティファクトは、SDK の他の依存関係が要求する古いバージョンになる可能性がありました。埋め込み Java クライアント SDK は、Jackson をコンパイル時の依存関係として公開しなくなりました。アプリケーションが Jackson を直接使用していて、SDK が提供することに依存していた場合は、アプリケーションのビルドで Jackson を宣言してください。
- ScalarDB Cluster クライアントで書き込みバッファリングが有効な場合、終端されていない文字列リテラルの内側で終わる `INSERT` または `UPSERT` ステートメントは、後で別のステートメントとともに送信される時点やコミット時ではなく、実行時に拒否されるようになりました。

##### ScalarDB SQL

- `byte[]` から作成された BLOB 値の `Value.hashCode()` が `equals()` と一貫するように修正しました。この不整合により、主キーまたはインデックス列に対する同じ BLOB の等価条件をすべての `OR` グループで繰り返す `SELECT`、`UPDATE`、または `DELETE` ステートメントが、効率の悪いスキャンで計画されたり、クロスパーティションスキャンのフィルタリングが有効でない場合に失敗するクロスパーティションスキャンとして計画されたりする可能性がありました。
- 誤った BLOB 値が暗黙的に書き込まれたり比較されたりする可能性のある2つのバグを修正しました。ダイレクトモードでは、`BoundStatement.setBlob()`、`Value.ofBlob()`、`Value.of()`、または JDBC の `setObject()` メソッドを通じて `ByteBuffer` としてバインドされた BLOB 値が、使用されるたびにバッファの末尾まで読み取られていたため、複数の行を更新する `UPDATE` ステートメントや再実行されたステートメントが、空の BLOB を書き込んだり、BLOB 列を空の BLOB と比較したりしていました。JDBC ドライバーでは、`setBytes()` と `setObject()` がアプリケーションの配列またはバッファへの参照を保持していたため、バッチの各行で1つの配列またはバッファを再利用すると、すべての行に最後の内容が書き込まれていました。ScalarDB SQL は、これらの値を使用する際に、アプリケーションのバッファまたは配列を読み取る代わりにコピーするようになりました。この修正では、すでに影響を受けたデータは修復されません。
- セミコロンで始まる、2つ以上のセミコロンで終わる、またはキーワードと次の記号や文字列リテラルの間にスペースがない (`SELECT*FROM tbl` や `WITH'key'='value'` など) SQL が正しく読み取られないバグを修正しました。ScalarDB Cluster では、このような DML ステートメントの `WITH` 句の認証属性が無視され、ステートメントがクライアント設定の認証情報で実行されていました。手動コミットモードでは、JDBC ドライバーがこのような DML ステートメントを即座にコミットしていたため、ロールバックできませんでした。`COMMIT;;` のように前後にセミコロンがあるコマンドステートメントは受け入れられるようになり、`BEGIN WITH 'key'='value''` のように終端されていない文字列リテラルの内側で終わる SQL は、以前は異なる値で受け入れられていましたが、拒否されるようになりました。`USE` の名前空間名など、コマンドステートメント内の引用符なしのオブジェクト名は、SQL 文法と同様に、ASCII 文字で始まり、ASCII 文字、数字、アンダースコア、ドル記号のみを含む場合にのみ受け入れられるようになったため、それ以外の名前は引用符で囲んでください。
- `HAVING` 句内の無効な `LIKE` または `NOT LIKE` 述語が、ステートメントの計画時に拒否されない問題を修正しました。これまで、エスケープ文字で終わるなどの不正なパターンは、グループに対して述語が評価されたときにのみ `AssertionError` で失敗していたため、どのグループも述語に到達しない場合は同じステートメントが成功する可能性がありました。2文字以上のエスケープ文字列は、暗黙的に最初の文字として扱われていました。また、`TEXT` 以外の列または集計関数に対する `LIKE` 述語は、実行時にのみ失敗するか、`NULL` パターンの場合は行を返しませんでした。このような述語は、`WHERE` 句と同じパターンおよびエスケープのチェックによって、レコードを読み取る前のステートメントの計画時に拒否されるようになりました。`TEXT` ターゲットに対する `NULL` パターンは、引き続きどのグループにも一致しません。
- `GROUP BY` 句も集計関数もない `SELECT` ステートメントの `HAVING` 句が暗黙的に無視され、ステートメントが `WHERE` 句に一致するすべての行を返す問題を修正しました。SQL 標準と同様に、`HAVING` 句のみがある場合はすべての行が1つのグループになるため、このようなステートメントは、`GROUP BY` 句にも集計関数にも含まれない列を選択する他のステートメントと同じエラーで拒否されるようになりました。そのため、以前は行を返していたステートメントが失敗する可能性があります。行をフィルタリングするには、条件を `WHERE` 句に移動してください。`GROUP BY` 句または集計関数を持つステートメントは影響を受けません。そのような列のエラーメッセージには、内部の詳細ではなく、記述されたとおりの列が表示されるようになりました。

## v3.20.0

**発売日:** 2026年10月30日

### まとめ

このリリースでは、ScalarDB Cluster 上の ScalarDB SQL に対するグローバルトランザクションのサポートを導入し、複数のプロセスやマイクロサービスにまたがるトランザクションを可能にしました。また、PostgreSQL ワイヤープロトコルのサポートを追加し、PostgreSQL ドライバーを使用するアプリケーションやツールが ScalarDB Cluster に接続できるようにしました。さらに、このリリースでは Consensus Commit のトランザクション性能と信頼性を向上させ、トランザクションのライフサイクル管理を簡素化し、従来のトランザクション API を削除し、ストレージアダプター操作の正確性と信頼性を強化しました。また、SQL Server 2025 のサポートを追加し、SQL Server 2017 のサポートを終了し、認証および認可の修正や脆弱性の緩和を通じてセキュリティを強化しました。

### Community edition

#### 機能強化

- Consensus Commit は、連続する Get 操作をバッチ内で並列に実行するようになりました。これは `scalar.db.consensus_commit.parallel_batch_get.enabled` と `scalar.db.consensus_commit.parallel_batch_get.max_concurrency_per_batch` で設定できます。 ([#4053](https://github.com/scalar-labs/scalardb/pull/4053))

#### 改善点

- `BranchTransaction.end()` を `BranchTransaction.end(BranchTransaction.Status)` に置き換えました。これにより、グローバルトランザクションのブランチは、その処理の結果を宣言する必要があります。既存の `end()` 呼び出しを `end(BranchTransaction.Status.SUCCESS)` に置き換え、失敗時のパスでは `end(BranchTransaction.Status.FAILURE)` を呼び出してください。 ([#3806](https://github.com/scalar-labs/scalardb/pull/3806))
- AWS Advanced JDBC Wrapper のサポートを追加し、Aurora PostgreSQL および Aurora MySQL 向けの高速な Aurora フェイルオーバーを有効にしました。例外オーバーライドを指定して HikariCP を設定することは、結果が不明なトランザクションが確定的な失敗として報告される原因となるため、起動時に拒否されるようになりました。 ([#3805](https://github.com/scalar-labs/scalardb/pull/3805))
- Cosmos DB のエラーメッセージに Cosmos DB の診断情報が含まれていたため、メッセージが過度に大きくなり、エラー情報が失われる可能性があった問題を修正しました。 ([#3816](https://github.com/scalar-labs/scalardb/pull/3816))
- `DistributedTransactionManager.join()` と `DistributedTransactionManager.resume()` およびそれらの実装を非推奨とし、3.20.0 で削除することにしました。 ([#3817](https://github.com/scalar-labs/scalardb/pull/3817))

### Enterprise edition

#### 機能強化

##### ScalarDB Cluster

- ScalarDB Cluster 上の ScalarDB SQL に対するグローバルトランザクションのサポートを追加しました。`SqlSession` と JDBC ドライバーの新しい `GLOBAL_TRANSACTION` モードにより、アプリケーションは、マイクロサービストランザクションのように、複数のプロセスにまたがる単一のトランザクションを実行できます。1つのプロセスがグローバルトランザクションを開始し、各プロセスが `BEGIN BRANCH` と `END BRANCH` でそのブランチを実行します。Transaction Coordinator で `scalar.db.sql.enabled` が `true` に設定されている場合、Transaction Coordinator がそれらに代わって ScalarDB Cluster 間で2フェーズコミットを実行します。同じアプリケーションコードは、単一の ScalarDB Cluster 内のトランザクションでも動作し、どちらになるかは設定のみで選択されます。
- ScalarDB Cluster に PostgreSQL ワイヤープロトコルのサポートを追加しました。`scalar.db.postgres.enabled` が `true` に設定されている場合、各ノードは `scalar.db.postgres.port` で指定されたポート (デフォルトは `5432`) で PostgreSQL 接続を受け付けるため、psql、PostgreSQL JDBC ドライバーなどの PostgreSQL ドライバー、およびその他の PostgreSQL ツールから ScalarDB Cluster 上で SQL を実行できます。認証が有効な場合、クライアントは ScalarDB Cluster ユーザーとしてパスワード、またはパスワードとして送信される OIDC アクセストークンでログインし、ScalarDB Cluster は他のクライアントと同様に、それらのユーザーの権限を適用します。`scalar.db.postgres.auth` を使用することで、パスワードのみ (`userpass`)、または OIDC アクセストークンのみ (`oidc_jwt`) を許可できます。認証が有効な場合、デフォルトでは接続に TLS を使用する必要があり、他の指定がない限り、ノードの TLS 証明書と秘密鍵が使用されます。

##### ScalarDB SQL

- JOIN を使用した SELECT 文の WHERE 句で、結合されたテーブルの列を参照するためのサポートを追加しました。
- JDBC ドライバーの `Connection.rollback()` を修正し、ロールバックが失敗した場合に `SQLException` をスローするようにしました。以前は、チェックされない ScalarDB SQL 例外をそのままスローしていました。`Connection.commit()` は、自動コミットモードなど、進行中のトランザクションがない場合に、SQLState が `SDB99` の `SQLException` ではなく、SQLState が `SDB01` の `SQLNonTransientException` をスローするようになりました。また、デフォルトの名前空間が存在しないなどの理由で接続の作成に失敗した場合に、キャッシュされたセッションファクトリーの有効期限が切れなくなる問題も JDBC ドライバーで修正しました。

#### 改善点

##### ScalarDB Cluster

- 属性ベースのアクセス制御メタデータキャッシュがリフレッシュされる際に発行されるクエリの数を削減し、各リフレッシュ後の最初のリクエストで発生するレイテンシスパイクを解消しました。
- `BranchTransaction.end()` を `BranchTransaction.end(BranchTransaction.Status)` に置き換えた ScalarDB Core の変更を採用しました。これにより、グローバルトランザクションのブランチは、その処理の結果を宣言する必要があります。既存の `end()` 呼び出しを `end(BranchTransaction.Status.SUCCESS)` に置き換え、失敗時のパスでは `end(BranchTransaction.Status.FAILURE)` を呼び出してください。
- OIDC JWT の検証を修正し、JWKS 取得のレート制限を使い果たした場合に、内部エラーではなく認証失敗として報告されるようにしました。
- 3.19.0 で非推奨となっていた `ClusterClientTransactionManager.join()`、`ClusterClientTransactionManager.resume()`、および `ClusterClientSqlTransactionManager.resume()` を削除しました。内部使用向けだった `SINGLETON` クラスタークライアントモード (`singleton:` コンタクトポイント) を削除しました。
- Global Transaction API を修正し、`GlobalTransactionManager.begin` に渡される認証属性が、開始、および開始者のコミットとロールバックに使用する資格情報を選択するようにし、トランザクション属性としてクラスターに転送されないようにしました。
- ロールバックまたはその他の終端操作が、認証トークンの有効期限切れにより拒否された場合に、トランザクションまたはトランザクション参加者のコンテキストが、クラスターノードのメモリ内に無期限に残る可能性がある問題を修正しました。また、実行中のトランザクションのコミットが失敗した場合に、クラスターの一時停止がトランザクションの有効期限を待たなくなりました。
- Rollback RPC を変更し、すでに終了しているトランザクションなど、クラスターノードが認識していないトランザクションをロールバックする場合に、`NOT_FOUND` エラーを返さずに成功するようにしました。
- 暗号化列の関連データの生成方法を簡素化しました。生成される値は変わりません。
- コミットが結果にかかわらずトランザクションを終了するように変更しました。これにより、コミットが失敗した後にトランザクションをロールバックする必要がなくなります。コミット後のロールバックまたはアボートは、コミットが成功したか失敗したかにかかわらず、何も行わず、クラスターにリクエストを送信しません。
- Global Transaction API の Transaction Coordinator バッキングを修正し、1つの `GlobalTransactionManager` 内で同時に開かれている同じトランザクションのブランチが、それぞれ独自の資格情報として実行されるようにしました。以前は、このようなブランチが、別のブランチの資格情報またはデフォルトの資格情報で実行される可能性がありました。

##### ScalarDB GraphQL

- 2フェーズコミットのサポートを削除しました。`@twoPhaseCommit` ディレクティブと `prepare`、`validate`、`commit` ミューテーションフィールド、および2フェーズコミットトランザクションマネージャー用の `GraphQlFactory` コンストラクターパラメーターがなくなりました。この機能は以前のリリースで非推奨にはなっていませんでした。`@transaction` ディレクティブと `abort` および `rollback` ミューテーションフィールドは影響を受けません。
- 組み込み用に、`ResumableDistributedTransactionManager` と `DistributedTransactionAdmin` を受け取る `GraphQlServer` コンストラクターを追加しました。`GraphQlFactory` と `TransactionInstrumentation` のコンストラクターは、`DistributedTransactionManager` ではなく `ResumableDistributedTransactionManager` を受け取るようになりました。`@transaction` ディレクティブの動作は変わりません。
- コミットが結果にかかわらずトランザクションを終了するように変更しました。これにより、コミットが失敗した後にトランザクションをアボートする必要がなくなります。コミットなどによってすでに終了しているトランザクションの `abort` または `rollback` は、コミットが成功したか失敗したかにかかわらず、エラーではなく `true` を返すようになりました。

##### ScalarDB SQL

- 3.19.0 で非推奨となっていた `SqlTransactionManager.join()`、`SqlTransactionManager.resume()`、`SqlSession.join()`、`SqlSession.suspend()`、`SqlSession.resume()`、`StatementBuilder.join()`、`StatementBuilder.suspend()`、`StatementBuilder.resume()`、および `JOIN`、`SUSPEND`、`RESUME` 文を削除しました。Spring Data 統合の `ScalarDbRepositoryImpl` から `begin()`、`commit()`、`rollback()`、`join()`、`resume()`、`suspend()` を削除しました。また、`ScalarDbJdbcAggregateTemplate` からも同じメソッドを削除し、その public コンストラクターは `NamedParameterJdbcOperations` を受け取らなくなりました。
- コミットが結果にかかわらずトランザクションを終了するように変更しました。これにより、コミットが失敗した後にトランザクションをロールバックする必要がなくなります。コミット後のロールバックまたはアボートは、コミットが成功したか失敗したかにかかわらず、何も行いません。すでに終了しているトランザクションに対する文またはコミットは、すべての接続モードで `IllegalStateException` で失敗するようになりました。
- トランザクションの進行中は DDL 文と DCL 文を拒否するように変更しました。以前は、このような文は即座に有効になり、トランザクションとともにロールバックされませんでした。DDL または DCL を実行する前に、トランザクションをコミットまたはロールバックしてください。
- ScalarDB SQL 自身が比較する TEXT 値の順序 (`ORDER BY`、`MIN`、`MAX`、`HAVING` の範囲条件、および結合後の `WHERE` の範囲条件) を、UTF-8 データのバイナリ照合順序と一致する Unicode コードポイント順に変更しました。以前は、U+FFFF を超える文字が U+E000 から U+FFFF の文字よりも前に並べられていました。

### ScalarDB Analytics

このリリースには、多くの改善点、セキュリティ問題の修正、およびバグ修正が含まれています。

:::warning 破壊的変更

- データソース登録時に、ソースタイプがサポートされていないために除外された列を報告するようになりました。`RegisterResponse` はスキップされた列ごとに1つの `warnings` エントリを持ち、Java SDK の `DataSourceClient.register` は登録されたデータソースとスキップされた列を持つ `RegisterDataSourceResult` を返し、CLI の `data-source register` は登録されたデータソースの後にそれらを stderr に出力します (https://github.com/scalar-labs/scalardb-analytics/pull/56)
- サーバーイメージの `/scalardb-analytics-server` および CLI イメージの `/scalardb-analytics-cli` 以下のアプリケーションファイルは root が所有するようになったため、ランタイムユーザーはこれらのディレクトリ内のイメージ提供ファイルを変更したり、ファイルを作成したりできなくなりました。イメージ自身のアプリケーションディレクトリに書き込むデプロイメントは、書き込み可能なボリュームまたは他の書き込み可能な場所を使用する必要があります。これらのディレクトリ以下を含む既存のバインドマウントおよびボリュームは、それぞれの権限を保持し、UID/GID 201 がアクセスできる場合は移動する必要はありません (https://github.com/scalar-labs/scalardb-analytics/pull/73)
- サーバー配布物の `without-licensing` を `app` に、対応するイメージを `ghcr.io/scalar-labs/scalardb-analytics-server-without-licensing` から `ghcr.io/scalar-labs/scalardb-analytics-server` にそれぞれ変更しました (https://github.com/scalar-labs/scalardb-analytics/pull/2)
- `com.scalar.db.analytics.spark.ScalarDbAnalyticsCatalog` は、使用量計測サービスや計測用 Spark リスナーを必要としなくなりました。サーバーイメージはポート 11051 のみを公開します (https://github.com/scalar-labs/scalardb-analytics/pull/2)
- CLI の `permission list` は、リソースタイプ、権限レベル、カタログ、データソース、名前空間、およびテーブル名の形式で各権限を表示するようになりました。これにより、従来の生の権限名とリソース ID ではなく、`permission grant` が受け取る形式で表示されます。gRPC のレスポンスおよび Java SDK の `EffectivePermission` もリソース名を保持します (https://github.com/scalar-labs/scalardb-analytics/pull/58)
- スキーマ内の名前空間、テーブル、列、または列型の名前に制御文字 (Unicode カテゴリ Cc、改行や ESC など) または双方向書式文字 (U+202A から U+202E、U+2066 から U+2069) が含まれている場合、データソースの登録はそのままの名前で登録するのではなく、`DB-ANALYTICS-10401` で失敗するようになりました。エラーはフィールドとそのパスを示し、文字はエスケープされます。印刷可能な Unicode 名は従来通り受け入れられます (https://github.com/scalar-labs/scalardb-analytics/pull/60)
