# ScalarDB 3.20 リリースノート

このページには、ScalarDB 3.20 のリリースノートのリストが含まれています。

## v3.20.0

**発売日:** 2026年10月30日

### まとめ

このリリースでは、ScalarDB Cluster 上の ScalarDB SQL に対するグローバルトランザクションのサポートを導入し、複数のプロセスやマイクロサービスにまたがるトランザクションを可能にしました。また、PostgreSQL ワイヤープロトコルのサポートを追加し、PostgreSQL ドライバーを使用するアプリケーションやツールが ScalarDB Cluster に接続できるようにしました。さらに、このリリースでは Consensus Commit のトランザクション性能と信頼性を向上させ、トランザクションのライフサイクル管理を簡素化し、従来のトランザクション API を削除し、ストレージアダプター操作の正確性と信頼性を強化しました。また、SQL Server 2025 のサポートを追加し、SQL Server 2017 のサポートを終了し、認証および認可の修正や脆弱性の緩和を通じてセキュリティを強化しました。

### Community edition

#### 機能強化

- Consensus Commit は、連続する Get 操作をバッチ内で並列に実行するようになりました。これは `scalar.db.consensus_commit.parallel_batch_get.enabled` と `scalar.db.consensus_commit.parallel_batch_get.max_concurrency_per_batch` で設定できます。 ([#4053](https://github.com/scalar-labs/scalardb/pull/4053))

#### 改善点

- `BranchTransaction.end()` を `BranchTransaction.end(BranchTransaction.Status)` に置き換えました。これにより、グローバルトランザクションのブランチは、その処理の結果を宣言する必要があります。既存の `end()` 呼び出しを `end(BranchTransaction.Status.SUCCESS)` に置き換え、失敗時のパスでは `end(BranchTransaction.Status.FAILURE)` を呼び出してください。 ([#3806](https://github.com/scalar-labs/scalardb/pull/3806))
- AWS Advanced JDBC Wrapper のサポートを追加し、Aurora PostgreSQL および Aurora MySQL 向けの高速な Aurora フェイルオーバーを有効にしました。例外オーバーライドを指定して HikariCP を設定することは、結果が不明なトランザクションが確定的な失敗として報告される原因となるため、起動時に拒否されるようになりました。 ([#3805](https://github.com/scalar-labs/scalardb/pull/3805))
- Cosmos DB のエラーメッセージに Cosmos DB の診断情報が含まれていたため、メッセージが過度に大きくなり、エラー情報が失われる可能性があった問題を修正しました。 ([#3816](https://github.com/scalar-labs/scalardb/pull/3816))
- `DistributedTransactionManager.join()` と `DistributedTransactionManager.resume()` およびそれらの実装を非推奨とし、3.20.0 で削除することにしました。 ([#3817](https://github.com/scalar-labs/scalardb/pull/3817))
- スキャナーがすでに返したレコードの更新と削除を許可しました。これにより、アプリケーションは `scan()` で結果全体をバッファリングする代わりに、スキャナーを反復処理しながら行を変更できます。スキャン範囲への挿入は引き続き許可されません。 ([#3850](https://github.com/scalar-labs/scalardb/pull/3850))
- JDBC データベースでの単一の put 操作または delete 操作におけるロック待機タイムアウトやシリアライゼーション失敗などの競合エラーが、リトライ可能として分類されなかった問題を修正しました。その結果、Consensus Commit は、コミット中のこのような競合を `CommitException` や `UnknownTransactionStatusException` ではなく `CommitConflictException` として報告できるようになりました。 ([#3852](https://github.com/scalar-labs/scalardb/pull/3852))
- Consensus Commit のレコードリカバリーを修正し、基盤となるストレージによって報告された競合エラーをリトライし、解消しない競合は競合として報告することで、トランザクションをリトライできるようにしました。 ([#3853](https://github.com/scalar-labs/scalardb/pull/3853))
- 未完了のトランザクションのレコードを保持しているキーに対して、レコードを作成する書き込み操作が失敗し続ける問題を修正しました。このようなレコードは、書き込みが失敗した際にリカバリーされるようになり、リトライが成功します。 ([#3868](https://github.com/scalar-labs/scalardb/pull/3868))
- トランザクションのコミットおよびロールバックの性能を向上させました。ロールバックするレコードは並列で読み取られるようになり、非同期コミットまたはロールバックが有効な場合、レコードのコミットとロールバックはトランザクションのスレッドで実行されなくなりました。 ([#3888](https://github.com/scalar-labs/scalardb/pull/3888))
- 3.19.0 で非推奨となっていた `DistributedTransactionManager.join()` と `DistributedTransactionManager.resume()` を削除しました。`scalar.db.active_transaction_management.enabled` を `scalar.db.two_phase_commit.active_transaction_management.enabled` に名称変更し、2フェーズコミットのコーディネーターと参加者にのみ適用されるようにしました。`scalar.db.active_transaction_management.expiration_time_millis` のデフォルト値を `-1` から `60000` に変更しました。 ([#3889](https://github.com/scalar-labs/scalardb/pull/3889))
- ScalarDB によって作成される新しい Cosmos DB コンテナーは、メタデータおよび名前空間コンテナーを含め、パーティションキー定義 V2 を使用します。既存のコンテナーは、テーブルが修復される場合でも、現在のパーティションキー定義を維持します。既存のコンテナーを V2 に移行するには、そのデータを新しいコンテナーにコピーしてください。 ([#3870](https://github.com/scalar-labs/scalardb/pull/3870))
- テーブルが存在するかどうかを確認する処理の性能を向上させました。`tableExists()` は、名前空間内のテーブルを一覧表示する代わりに、指定されたテーブルのメタデータのみを読み取るようになり、そのコストはテーブル数に応じて増加しなくなりました。その結果、DynamoDB では、ScalarDB のメタデータを持たないテーブルは存在するものとして報告されなくなりました。また、ScalarDB のメタデータテーブルまたはコンテナーが存在しない場合に、DynamoDB と Cosmos DB の `getTableMetadata()` が `null` を返さずに例外をスローする問題を修正しました。そのため、これらのストレージでは、「テーブルが見つかりません」というエラーは、メタデータテーブルまたはコンテナー自体が存在しないことを意味する場合もあります。このようなテーブルが AWS コンソールまたは Azure ポータルで確認できる場合は、`repairTable()` を実行する前に、`scalar.db.system_namespace_name` (DynamoDB の場合は名前空間プレフィックスも) がすべての設定で一致していることを確認してください。 ([#3947](https://github.com/scalar-labs/scalardb/pull/3947))
- コミットが結果にかかわらずトランザクションを終了するように変更しました。これにより、コミットが失敗した後にトランザクションをロールバックする必要がなくなります。コミット後のロールバックまたはアボートは、コミットが成功したか失敗したかにかかわらず、再度ロールバックしたり `IllegalStateException` をスローしたりせず、何も行いません。 ([#3966](https://github.com/scalar-labs/scalardb/pull/3966))
- SQL Server JDBC ドライバーを 13.6.0 にアップグレードし、1582年10月15日より前の日付の TIMESTAMPTZ 値が SQL Server に最大10日ずれて保存される問題を修正しました。以前のバージョンの ScalarDB によって SQL Server に保存された、1582年10月15日より前の日付の TIMESTAMPTZ 値は、書き込まれた値よりも最大10日早い値として読み取られます。このようなデータがある場合は、ずれを解消するために移行を検討してください。 ([#3971](https://github.com/scalar-labs/scalardb/pull/3971))
- SQL Server 2025 のサポートを追加し、SQL Server 2017 のサポートを終了しました。 ([#3998](https://github.com/scalar-labs/scalardb/pull/3998))
- JDBC アダプターでの upsert が各列の値を1回だけ送信するように変更し、MySQL と MariaDB でより大きな BLOB 値を使用できるようにしました。 ([#4040](https://github.com/scalar-labs/scalardb/pull/4040))
- テーブルのインポートで、TEXT の照合順序に従えない列タイプを拒否するように変更しました。対象は、SQL Server の `nchar`、`nvarchar`、`text`、`ntext`、Oracle の `NCHAR` と `NVARCHAR2`、および Db2 の `GRAPHIC`、`VARGRAPHIC`、`DBCLOB` です。 ([#4051](https://github.com/scalar-labs/scalardb/pull/4051))
- ブランチが属するグローバルトランザクションの ID を返す `BranchTransaction.getGlobalTransactionId()` を追加しました。`BranchTransaction.getId()` はブランチ自体の ID を表すようになったため、グローバルトランザクションの ID が必要な場合は `getGlobalTransactionId()` を使用してください。`getId()` は `getGlobalTransactionId()` と同じ ID を返す場合があるため、グローバルトランザクションのブランチを区別するために使用しないでください。 ([#4059](https://github.com/scalar-labs/scalardb/pull/4059))
- `LIKE` または `NOT_LIKE` を使用したミューテーション条件が操作の検証を通過した後、ストレージで `AssertionError` により失敗する問題を修正しました。このような条件は `IllegalArgumentException` で拒否されるようになりました。 ([#4072](https://github.com/scalar-labs/scalardb/pull/4072))
- ScalarDB 自身が比較する TEXT 値の順序を、UTF-8 データのバイナリ照合順序と一致する Unicode コードポイント順に変更しました。以前は、補助文字 (U+10000 以上) が U+E000 から U+FFFF の文字よりも前に並べられていました。SQL Server では、TEXT 列に対する範囲スキャンが列の照合順序に従うように、文字列パラメーターが `VARCHAR` として送信されるようになりました。 ([#4075](https://github.com/scalar-labs/scalardb/pull/4075))
- S3 および Cloud Storage アダプターを改善し、テーブルの切り捨てまたは削除時に、一時的なエラーで失敗したオブジェクトの削除をリトライするようにしました。 ([#4077](https://github.com/scalar-labs/scalardb/pull/4077))
- 影響を受ける emSign ルート CA をすべてのコンテナーイメージの cacerts から削除することで、[CVE-2026-91403](https://github.com/advisories/GHSA-9h75-rf66-wh3r "CVE-2026-91403") と [CVE-2026-114820](https://github.com/advisories/GHSA-255q-pwv4-fjj7 "CVE-2026-114820") (eMudhra CA の侵害) を緩和しました。また、ScalarDB Schema Loader および ScalarDB Data Loader CLI コンテナーイメージのベースイメージを Java 8 (Eclipse Temurin 8) から Java 21 (Eclipse Temurin 21) に更新しました。イメージにはデフォルトで JVM オプションが設定されていないため、影響を受けるのは Java 8 固有の JVM オプション (例: `JAVA_TOOL_OPTIONS` 経由の `-XX:+PrintGCDateStamps`) を渡しているユーザーのみで、そのようなオプションを渡すと JVM が起動しなくなります。 ([#4112](https://github.com/scalar-labs/scalardb/pull/4112))

#### バグの修正

- Oracle で SERIALIZABLE 分離レベルを使用する場合の `ORA-08177` など、競合エラーによりスキーマ操作が失敗する可能性がある問題を修正しました。競合エラーは再試行されるようになりました。 ([#3820](https://github.com/scalar-labs/scalardb/pull/3820))
- Cloud Storage アダプターの get 操作が同時書き込みを処理できるように修正しました。 ([#3851](https://github.com/scalar-labs/scalardb/pull/3851))
- 期限切れまたは削除されたトランザクションの自動ロールバックを含め、スキャナーが開いている Consensus Commit トランザクションをロールバックすると、IllegalArgumentException で失敗し、残りのスキャナーが開いたままになり、グループコミットのスロットが解放されない可能性がある問題を修正しました。 ([#3867](https://github.com/scalar-labs/scalardb/pull/3867))
- Cassandra アダプターを修正し、条件付き書き込みによって適用された更新が、同じレコードに対する直前の条件なし書き込みと同じミリ秒内に実行された場合でも、暗黙のうちに破棄されないようにしました。アダプターは、書き込みタイムスタンプをサーバーから取得し、パーティションに対するすべてのリクエストを同じレプリカに送信するようになりました。 ([#3890](https://github.com/scalar-labs/scalardb/pull/3890))
- Consensus Commit が、条件付きミューテーションの無効な条件を拒否せずに受け入れていた問題を修正しました。 ([#3871](https://github.com/scalar-labs/scalardb/pull/3871))
- DynamoDB で、AWS SDK がリトライした単一の条件付き書き込みが、実際には適用されていたにもかかわらず、適用されなかったと報告される可能性がある問題を修正しました。このような書き込みは、結果が不明として報告されるようになりました。また、DynamoDB 操作の一部の失敗が、`ExecutionException` ではなく、チェックされない AWS SDK 例外としてスローされる問題も修正しました。 ([#3922](https://github.com/scalar-labs/scalardb/pull/3922))
- トランザクションのコミット時に、Coordinator の状態書き込みがリトライされ、同時にそのトランザクションに対して `finishTransaction` が呼び出された場合に、競合が報告され、すでにコミット済みのレコードがロールバックされる可能性がある問題を修正しました。コミットは、代わりにトランザクションの状態が不明であることを報告するようになりました。 ([#3923](https://github.com/scalar-labs/scalardb/pull/3923))
- Cassandra、Cosmos DB、DynamoDB、および Object Storage で、`!=`、`<`、または `<=` 演算子を使用したスキャン条件が NULL の列値によって満たされてしまう問題を修正しました。また、Cassandra、DynamoDB、Consensus Commit の `PutIf` または `DeleteIf`、および Consensus Commit の `UpdateIf` で、`!=` 条件が NULL の列値によって満たされてしまう問題も修正しました。 ([#3930](https://github.com/scalar-labs/scalardb/pull/3930))

- Amazon S3 を使用する Object Storage アダプターで、AWS SDK がリトライした条件付き書き込みが、実際には適用されていたにもかかわらず、競合として報告される可能性がある問題を修正しました。このような書き込みは、結果が不明として報告されるようになりました。 ([#3958](https://github.com/scalar-labs/scalardb/pull/3958))
- Azure Blob Storage を使用する Object Storage アダプターで、Azure SDK がリトライした条件付き書き込みが、実際には適用されていたにもかかわらず、競合として報告される可能性がある問題を修正しました。このような書き込みは、結果が不明として報告されるようになりました。 ([#3964](https://github.com/scalar-labs/scalardb/pull/3964))
- Google Cloud Storage を使用する Object Storage アダプターで、Cloud Storage クライアントがリトライした削除が、実際には適用されていたにもかかわらず、競合として報告される可能性がある問題を修正しました。このような削除は1回だけ送信されるようになり、条件が満たされなかった以外の失敗は、結果が不明として報告されます。 ([#3965](https://github.com/scalar-labs/scalardb/pull/3965))
- アクティブなトランザクション管理がリクエストをまたいでスキャナーを保持している間に、クライアントがそのスキャナーを放棄した場合に、トランザクション外で開かれたスキャナーが閉じられなかった問題を修正しました。このようなスキャナーは、データベース接続や開いているデータベーストランザクションなど、トランザクションとストレージのリソースを保持し続けていました。現在は、アクティブなトランザクションの有効期限の間使用されなかった場合、またはアクティブなトランザクションの最大数を超える数のそのようなスキャナーが開いている場合に、そのスキャナーが閉じられます。 ([#3992](https://github.com/scalar-labs/scalardb/pull/3992))

### Enterprise edition

#### 機能強化

##### ScalarDB Cluster

- ScalarDB Cluster 上の ScalarDB SQL に対するグローバルトランザクションのサポートを追加しました。`SqlSession` と JDBC ドライバーの新しい `GLOBAL_TRANSACTION` モードにより、アプリケーションは、マイクロサービストランザクションのように、複数のプロセスにまたがる単一のトランザクションを実行できます。1つのプロセスがグローバルトランザクションを開始し、各プロセスが `BEGIN BRANCH` と `END BRANCH` でそのブランチを実行します。Transaction Coordinator で `scalar.db.sql.enabled` が `true` に設定されている場合、Transaction Coordinator がそれらに代わって ScalarDB Cluster 間で2フェーズコミットを実行します。同じアプリケーションコードは、単一の ScalarDB Cluster 内のトランザクションでも動作し、どちらになるかは設定のみで選択されます。
- ScalarDB Cluster に PostgreSQL ワイヤープロトコルのサポートを追加しました。`scalar.db.postgres.enabled` が `true` に設定されている場合、各ノードは `scalar.db.postgres.port` で指定されたポート (デフォルトは `5432`) で PostgreSQL 接続を受け付けるため、psql、PostgreSQL JDBC ドライバーなどの PostgreSQL ドライバー、およびその他の PostgreSQL ツールから ScalarDB Cluster 上で SQL を実行できます。認証が有効な場合、クライアントは ScalarDB Cluster ユーザーとしてパスワード、またはパスワードとして送信される OIDC アクセストークンでログインし、ScalarDB Cluster は他のクライアントと同様に、それらのユーザーの権限を適用します。`scalar.db.postgres.auth` を使用することで、パスワードのみ (`userpass`)、または OIDC アクセストークンのみ (`oidc_jwt`) を許可できます。認証が有効な場合、デフォルトでは接続に TLS を使用する必要があり、他の指定がない限り、ノードの TLS 証明書と秘密鍵が使用されます。

##### ScalarDB SQL

- JOIN を使用した SELECT 文の WHERE 句で、結合されたテーブルの列を参照するためのサポートを追加しました。
- JDBC ドライバーの `Connection.rollback()` を修正し、ロールバックが失敗した場合に `SQLException` をスローするようにしました。以前は、チェックされない ScalarDB SQL 例外をそのままスローしていました。`Connection.commit()` は、自動コミットモードなど、進行中のトランザクションがない場合に、SQLState が `SDB99` の `SQLException` ではなく、SQLState が `SDB01` の `SQLNonTransientException` をスローするようになりました。また、デフォルトの名前空間が存在しないなどの理由で接続の作成に失敗した場合に、キャッシュされたセッションファクトリーの有効期限が切れなくなる問題も JDBC ドライバーで修正しました。

#### 改善点

##### ScalarDB Cluster

- 属性ベースのアクセス制御メタデータキャッシュがリフレッシュされる際に発行されるクエリの数を削減し、各リフレッシュ後の最初のリクエストで発生するレイテンシスパイクを解消しました。
- `BranchTransaction.end()` を `BranchTransaction.end(BranchTransaction.Status)` に置き換えた ScalarDB Core の変更を採用しました。これにより、グローバルトランザクションのブランチは、その処理の結果を宣言する必要があります。既存の `end()` 呼び出しを `end(BranchTransaction.Status.SUCCESS)` に置き換え、失敗時のパスでは `end(BranchTransaction.Status.FAILURE)` を呼び出してください。
- OIDC JWT の検証を修正し、JWKS 取得のレート制限を使い果たした場合に、内部エラーではなく認証失敗として報告されるようにしました。
- 3.19.0 で非推奨となっていた `ClusterClientTransactionManager.join()`、`ClusterClientTransactionManager.resume()`、および `ClusterClientSqlTransactionManager.resume()` を削除しました。内部使用向けだった `SINGLETON` クラスタークライアントモード (`singleton:` コンタクトポイント) を削除しました。
- Global Transaction API を修正し、`GlobalTransactionManager.begin` に渡される認証属性が、開始、および開始者のコミットとロールバックに使用する資格情報を選択するようにし、トランザクション属性としてクラスターに転送されないようにしました。
- ロールバックまたはその他の終端操作が、認証トークンの有効期限切れにより拒否された場合に、トランザクションまたはトランザクション参加者のコンテキストが、クラスターノードのメモリ内に無期限に残る可能性がある問題を修正しました。また、実行中のトランザクションのコミットが失敗した場合に、クラスターの一時停止がトランザクションの有効期限を待たなくなりました。
- Rollback RPC を変更し、すでに終了しているトランザクションなど、クラスターノードが認識していないトランザクションをロールバックする場合に、`NOT_FOUND` エラーを返さずに成功するようにしました。
- 暗号化列の関連データの生成方法を簡素化しました。生成される値は変わりません。
- コミットが結果にかかわらずトランザクションを終了するように変更しました。これにより、コミットが失敗した後にトランザクションをロールバックする必要がなくなります。コミット後のロールバックまたはアボートは、コミットが成功したか失敗したかにかかわらず、何も行わず、クラスターにリクエストを送信しません。
- Global Transaction API の Transaction Coordinator バッキングを修正し、1つの `GlobalTransactionManager` 内で同時に開かれている同じトランザクションのブランチが、それぞれ独自の資格情報として実行されるようにしました。以前は、このようなブランチが、別のブランチの資格情報またはデフォルトの資格情報で実行される可能性がありました。

##### ScalarDB GraphQL

- 2フェーズコミットのサポートを削除しました。`@twoPhaseCommit` ディレクティブと `prepare`、`validate`、`commit` ミューテーションフィールド、および2フェーズコミットトランザクションマネージャー用の `GraphQlFactory` コンストラクターパラメーターがなくなりました。この機能は以前のリリースで非推奨にはなっていませんでした。`@transaction` ディレクティブと `abort` および `rollback` ミューテーションフィールドは影響を受けません。
- 組み込み用に、`ResumableDistributedTransactionManager` と `DistributedTransactionAdmin` を受け取る `GraphQlServer` コンストラクターを追加しました。`GraphQlFactory` と `TransactionInstrumentation` のコンストラクターは、`DistributedTransactionManager` ではなく `ResumableDistributedTransactionManager` を受け取るようになりました。`@transaction` ディレクティブの動作は変わりません。
- コミットが結果にかかわらずトランザクションを終了するように変更しました。これにより、コミットが失敗した後にトランザクションをアボートする必要がなくなります。コミットなどによってすでに終了しているトランザクションの `abort` または `rollback` は、コミットが成功したか失敗したかにかかわらず、エラーではなく `true` を返すようになりました。

##### ScalarDB SQL

- 3.19.0 で非推奨となっていた `SqlTransactionManager.join()`、`SqlTransactionManager.resume()`、`SqlSession.join()`、`SqlSession.suspend()`、`SqlSession.resume()`、`StatementBuilder.join()`、`StatementBuilder.suspend()`、`StatementBuilder.resume()`、および `JOIN`、`SUSPEND`、`RESUME` 文を削除しました。Spring Data 統合の `ScalarDbRepositoryImpl` から `begin()`、`commit()`、`rollback()`、`join()`、`resume()`、`suspend()` を削除しました。また、`ScalarDbJdbcAggregateTemplate` からも同じメソッドを削除し、その public コンストラクターは `NamedParameterJdbcOperations` を受け取らなくなりました。
- コミットが結果にかかわらずトランザクションを終了するように変更しました。これにより、コミットが失敗した後にトランザクションをロールバックする必要がなくなります。コミット後のロールバックまたはアボートは、コミットが成功したか失敗したかにかかわらず、何も行いません。すでに終了しているトランザクションに対する文またはコミットは、すべての接続モードで `IllegalStateException` で失敗するようになりました。
- トランザクションの進行中は DDL 文と DCL 文を拒否するように変更しました。以前は、このような文は即座に有効になり、トランザクションとともにロールバックされませんでした。DDL または DCL を実行する前に、トランザクションをコミットまたはロールバックしてください。
- ScalarDB SQL 自身が比較する TEXT 値の順序 (`ORDER BY`、`MIN`、`MAX`、`HAVING` の範囲条件、および結合後の `WHERE` の範囲条件) を、UTF-8 データのバイナリ照合順序と一致する Unicode コードポイント順に変更しました。以前は、U+FFFF を超える文字が U+E000 から U+FFFF の文字よりも前に並べられていました。

- 認証方法に `USERPASS` が含まれていないユーザーが、ユーザー名/パスワード認証でログインできてしまう問題を修正しました。そのようなユーザーにユーザー名/パスワード認証が必要な場合は、ユーザーの認証方法に `USERPASS` を追加し、パスワードなしのログインを意図していない限り、パスワードを設定してください。この修正は、クラスター内のすべてのノードがアップグレードされた後に完全に有効になります。
- 認証が有効な場合に、クライアントが、認証トークンの有効期限が切れた後や失効した後、または READ 権限が取り消された後でも、開いているスキャナーからの読み取りを続けられる問題を修正しました。スキャナーからのフェッチは、READ 権限を再確認するようになりました。OIDC クライアントの場合、スキャン中に有効期限が切れた JWT は、get や scan と同様に、次のフェッチで認証エラーになります。`OidcJwtAccessTokenHolder` を通じて JWT を提供するクライアントは、新しい JWT を設定してスキャンを続行できます。
- 暗号化列を持つテーブルに対するバッチ `Get` および `Scan` 操作が、`associated_data_required` が有効で、プロジェクションにすべてのプライマリキー列が含まれていない場合に、`IllegalStateException` で失敗する問題を修正しました。
- grpc_health_probe バイナリをアップグレードしてセキュリティ問題を修正しました: [CVE-2026-56851](https://github.com/advisories/GHSA-gx9w-9qq8-m485 "CVE-2026-56851"), [CVE-2026-78667](https://github.com/advisories/GHSA-f4xw-m386-m277 "CVE-2026-78667"), CVE-2026-78669, [CVE-2026-84304](https://github.com/advisories/GHSA-vp52-pcj8-j9qc "CVE-2026-84304"), [CVE-2026-84445](https://github.com/advisories/GHSA-2v4p-qf9q-27wj "CVE-2026-84445"), and [CVE-2026-97031](https://github.com/advisories/GHSA-hq7w-2xrq-wp2j "CVE-2026-97031")

##### ScalarDB SQL

- ScalarDB SQL 自身が評価する BLOB の比較 (`ORDER BY`、`HAVING` の範囲条件、および結合後の `WHERE` の範囲条件) で、`0x80` 以上のバイトが `0x00` から `0x7F` のバイトよりも小さいものとして扱われていた問題を修正しました。
- `FLOAT` および `DOUBLE` 列に対する `MIN` と `MAX` が、値に `NaN` が含まれる場合、または `0.0` と `-0.0` の両方が含まれる場合に、行の順序に依存した結果を返す問題を修正しました。
