このページには、ScalarDB 3.19 のリリースノートのリストが含まれています。

## v3.19.2

**発売日:** 2026年10月30日

### まとめ

このリリースでは、SQL Server 2025 のサポートを追加し、SQL Server 2017 のサポートを終了しました。また、Consensus Commit におけるトランザクションの信頼性とエラー処理を改善し、グローバルトランザクション API を強化し、テーブルメタデータ操作を最適化し、ストレージアダプター操作の正確性と信頼性を向上させました。さらに、認証および認可の修正、依存関係のアップグレード、脆弱性の緩和によりセキュリティを強化し、ScalarDB SQL におけるリソース管理の問題、およびデータの比較と集計の問題に対処しました。

### Community edition

#### 改善点

- JDBC データベースでの単一の put または delete 操作におけるロック待機タイムアウトやシリアライズ失敗などの競合エラーが、再試行可能として分類されない問題を修正しました。その結果、Consensus Commit は、コミット中のそのような競合を `CommitException` または `UnknownTransactionStatusException` ではなく `CommitConflictException` として報告できるようになりました。 ([#3852](https://github.com/scalar-labs/scalardb/pull/3852))
- Consensus Commit のレコードリカバリが、基盤となるストレージによって報告された競合エラーを再試行し、解消されない競合を競合として報告して、トランザクションを再試行できるように修正しました。 ([#3853](https://github.com/scalar-labs/scalardb/pull/3853))
- テーブルが存在するかどうかを確認する処理のパフォーマンスを改善しました。`tableExists()` は、ネームスペース内のテーブルを一覧表示する代わりに、指定されたテーブルのメタデータのみを読み取るようになったため、そのコストはテーブル数に応じて増加しなくなりました。その結果、DynamoDB では、ScalarDB のメタデータを持たないテーブルは存在するものとして報告されなくなりました。また、ScalarDB のメタデータテーブルまたはコンテナーが存在しない場合に、DynamoDB および Cosmos DB の `getTableMetadata()` が `null` を返す代わりに例外をスローする問題も修正しました。そのため、これらのストレージでは、「テーブルが見つかりません」というエラーは、メタデータテーブルまたはコンテナー自体が存在しないことを意味する場合もあります。そのようなテーブルが AWS コンソールまたは Azure ポータルで確認できる場合は、`repairTable()` を実行する前に、すべての設定間で `scalar.db.system_namespace_name` (および DynamoDB の場合はネームスペースプレフィックス) が一致していることを確認してください。 ([#3947](https://github.com/scalar-labs/scalardb/pull/3947))
- SQL Server 2025 のサポートを追加し、SQL Server 2017 のサポートを終了しました。 ([#3998](https://github.com/scalar-labs/scalardb/pull/3998))
- テーブルのインポートで、TEXT の照合順序に従えない列タイプ(SQL Server の `nchar`、`nvarchar`、`text`、`ntext`、Oracle の `NCHAR` および `NVARCHAR2`、Db2 の `GRAPHIC`、`VARGRAPHIC`、`DBCLOB`)を拒否するように変更しました。 ([#4051](https://github.com/scalar-labs/scalardb/pull/4051))
- ブランチが属するグローバルトランザクションの ID を返す `BranchTransaction.getGlobalTransactionId()` を追加しました。`BranchTransaction.getId()` はブランチ自体の ID を表すようになったため、グローバルトランザクションの ID が必要な場合は `getGlobalTransactionId()` を使用してください。`getId()` は `getGlobalTransactionId()` と同じ ID を返す場合があるため、グローバルトランザクションのブランチを区別するために使用しないでください。 ([#4059](https://github.com/scalar-labs/scalardb/pull/4059))
- SQL Server JDBC ドライバーを 13.6.0 にアップグレードし、1582年10月15日より前の日付の TIMESTAMPTZ 値が SQL Server に最大10日ずれて保存される問題を修正しました。以前のバージョンの ScalarDB によって SQL Server に保存された、1582年10月15日より前の日付の TIMESTAMPTZ 値は、書き込まれた値より最大10日前の値として読み取られます。そのようなデータがある場合は、ずれを解消するためにデータの移行を検討してください。 ([#3971](https://github.com/scalar-labs/scalardb/pull/3971))
- S3 および Cloud Storage アダプターを改善し、テーブルの切り詰めまたは削除時に、一時的なエラーで失敗したオブジェクトの削除を再試行するようにしました。 ([#4077](https://github.com/scalar-labs/scalardb/pull/4077))
- すべてのコンテナイメージの cacerts から影響を受ける emSign ルート CA を削除することで、[CVE-2026-91403](https://github.com/advisories/GHSA-9h75-rf66-wh3r "CVE-2026-91403") および [CVE-2026-114820](https://github.com/advisories/GHSA-255q-pwv4-fjj7 "CVE-2026-114820") (eMudhra CA の侵害) を緩和し、ScalarDB Schema Loader および ScalarDB Data Loader CLI コンテナイメージのベースイメージを Java 8 (Eclipse Temurin 8) から Java 21 (Eclipse Temurin 21) に更新しました。イメージにはデフォルトで JVM オプションが設定されていないため、この変更の影響を受けるのは、Java 8 固有の JVM オプション (たとえば、`JAVA_TOOL_OPTIONS` 経由で指定する `-XX:+PrintGCDateStamps`) を渡しているユーザーのみです。これらのオプションを指定すると、JVM が起動に失敗するようになります。 ([#4112](https://github.com/scalar-labs/scalardb/pull/4112))

- DynamoDB の `repairTable()` が、たとえば `createTable()` または `createIndex()` がオートスケーリングを有効にする前に失敗した場合(Application Auto Scaling の権限が不足していた場合など)に、既存のグローバルセカンダリインデックスのオートスケーリングを有効にしない問題を修正しました。また、`repairTable()` は、テーブルの既存のオートスケーリング範囲を、指定された、またはデフォルトのリクエストユニットにリセットせずに維持するようになったため、`--ru` を指定せずに repair を実行しても、Coordinator テーブルを含む既存のテーブルのキャパシティが低下しなくなりました。既存のテーブルのオートスケーリング範囲を変更するには、AWS コンソールまたは CLI を使用してください。オートスケーリングを有効にした `createTable()` または `createIndex()` が以前に失敗した場合は、アップグレード後に、インデックスを含むスキーマと、作成時と同じリクエストユニットを指定して、`repairTable()` を再度実行してください。`repairTable()` (または `--repair-all` を指定した Schema Loader) が以前に `--ru` なしで、またはより小さいリクエストユニットで実行された場合は、Coordinator テーブルを含む既存のテーブルのオートスケーリング範囲を確認し、AWS コンソールまたは CLI で復元してください。`repairTable()` は既存のテーブルの範囲を変更しなくなったためです。 ([#3949](https://github.com/scalar-labs/scalardb/pull/3949))

### Enterprise edition

#### 改善点

##### ScalarDB Cluster

- OIDC JWT の検証を修正し、JWKS 取得のレート制限が使い果たされた場合に、内部エラーではなく認証失敗として報告されるようにしました。
- グローバルトランザクション API を修正し、`GlobalTransactionManager.begin` に渡される認証属性が、begin、および開始者のコミットとロールバックの資格情報を選択するようにし、トランザクション属性としてクラスターに転送されないようにしました。

## v3.19.1

**発売日:** 2026年9月2日

### まとめ

このリリースでは、グローバルトランザクション API を更新し、ブランチが作業の結果を明示的に宣言することを必須とし、高速な Aurora フェイルオーバーのための AWS Advanced JDBC Wrapper のサポートを追加し、Cosmos DB のエラー処理と ScalarDB Cluster の属性ベースの認証メタデータキャッシュのリフレッシュを改善し、`join()` および `resume()` トランザクション API を非推奨にし、スキーマ操作中の競合エラーに対するリトライ処理を追加し、セキュリティの脆弱性に対処するために grpc_health_probe をアップグレードしました。

### Community edition

#### 改善点

- `BranchTransaction.end()` を `BranchTransaction.end(BranchTransaction.Status)` に置き換え、グローバルトランザクションのブランチが自身の作業の結果を宣言することを必須にしました。既存の `end()` 呼び出しは `end(BranchTransaction.Status.SUCCESS)` に置き換え、失敗パスでは `end(BranchTransaction.Status.FAILURE)` を呼び出してください。 ([#3806](https://github.com/scalar-labs/scalardb/pull/3806))
- AWS Advanced JDBC Wrapper のサポートを追加し、Aurora PostgreSQL および Aurora MySQL 向けの高速な Aurora フェイルオーバーを有効にしました。例外オーバーライドを指定して HikariCP を設定することは、結果が不明なトランザクションが確定的な失敗として報告される原因となるため、起動時に拒否されるようになりました。 ([#3805](https://github.com/scalar-labs/scalardb/pull/3805))
- Cosmos DB のエラーメッセージに Cosmos DB の診断情報が含まれていたため、メッセージが過度に大きくなり、エラー情報が失われる可能性があった問題を修正しました。 ([#3816](https://github.com/scalar-labs/scalardb/pull/3816))
- `DistributedTransactionManager.join()` および `DistributedTransactionManager.resume()` を、その実装とともに非推奨にしました。3.20.0 で削除される予定です。 ([#3817](https://github.com/scalar-labs/scalardb/pull/3817))

## v3.19.0

**発売日:** 2026年8月2日

### まとめ

このリリースでは、Consensus Commit の回復機能として、書き込みセットのログ記録、トランザクションの完了、および単一レコード回復の API を追加し、コーディネーターの状態レコードがクリーンアップされる際の回復の正確性を改善しました。また、属性ベースの認証、OpenTelemetry サポート、分離クラスターデプロイメント向けのトランザクションコーディネーターノード、およびクラスタークライアント SDK でのグローバルトランザクション API サポートを追加しました。さらに、`repairTable`、アクティブトランザクション管理、クラスターのアップグレードと認証の動作、SQL SELECT の実行を改善し、Consensus Commit、クラスターのロールバック/一時停止、SQL ステートメントキャッシュに関するいくつかの問題を修正しました。

### Community edition

#### 機能強化

- オプトイン設定 `scalar.db.consensus_commit.coordinator.write_set_logging.enabled` を追加しました。有効にすると、コーディネーターテーブルに `tx_write_set` 列が追加され、コミット/アボート時に値が設定されます。これにより、事前トランザクション回復のための基盤が整います。既存のコーディネーターテーブルは、設定を有効にして `Admin.repairCoordinatorTables()` を実行することで移行できます。 ([#3570](https://github.com/scalar-labs/scalardb/pull/3570) [#3593](https://github.com/scalar-labs/scalardb/pull/3593))
- コミットされたトランザクションのレコードごとのコミット後回復を完了し、コーディネーターの状態行を削除する `DistributedTransactionManager#finishTransaction(String)` API を追加しました。トランザクションが完了した場合 (または既に完了していた場合) は `true` を返し、書き込みセットがないためトランザクションが適用できない場合 (例えば、`commit()` ではなく `rollback()` / `abort()` で終了したトランザクション) は `false` を返します。完了に失敗した場合は `TransactionException` がスローされます。これは Consensus Commit トランザクションマネージャー固有の低レベル操作 API です。ほとんどのアプリケーションは直接呼び出すべきではなく、高度なユースケースを対象としています。呼び出し元は、基礎となるトランザクションのライフサイクルとこのメソッドを直接呼び出す際の影響を理解していることが求められます。 ([#3567](https://github.com/scalar-labs/scalardb/pull/3567))
- クラッシュしたトランザクションによってコミットされていない状態に残された単一のレコードを回復するための `DistributedTransactionManager#recoverRecord` API を追加しました。これは Consensus Commit トランザクションマネージャー固有の低レベル操作 API です。ほとんどのアプリケーションは直接呼び出すべきではなく、高度なユースケースを対象としています。呼び出し元は、基礎となるトランザクションのライフサイクルとこのメソッドを直接呼び出す際の影響を理解していることが求められます。 ([#3617](https://github.com/scalar-labs/scalardb/pull/3617))

#### 改善点

- メタデータが既に最新の状態の場合にテーブルのメタデータの再書き込みをスキップする (Cosmos DB の場合は、コンテナーのインデックスポリシーが既に一致する場合にその更新もスキップする) ように `repairTable` を改善し、不要な書き込みを回避するようにしました。 ([#3613](https://github.com/scalar-labs/scalardb/pull/3613))

- **一時停止 RPC に `ABORTED` が新たに追加されました。** 以前はすべての一時停止の失敗は `FAILED_PRECONDITION` でしたが、別の管理リクエストとのレース競合による失敗は `ABORTED` となりました。これにより、一時停止を単純に再試行できます。すべての一時停止の失敗には、ステータストレーラーに `google.rpc.ErrorInfo` の詳細が含まれ、`domain` は `com.scalar.db.cluster.admin` に、`reason` は結果に設定されます。これにより、呼び出し元はステータスコードや説明テキストのマッチングなしに結果を区別できます。特に、失敗した一時停止から回復するために一時停止解除を行う呼び出し元は、`reason` が `TIMED_OUT_STILL_PAUSED` の場合はその一時停止解除をスキップする必要があります。これは、サーバーが以前のリクエストによって依然として一時停止されているためです。
