# ScalarDB 3.18 リリースノート

このページには、ScalarDB 3.18 のリリースノートのリストが含まれています。

## v3.18.4

**発売日:** 2026年11月11日

### まとめ

このリリースでは、より多くのデータベースで READ COMMITTED 分離レベルをサポートし、インポートされたテーブルの問題を修正することで、トランザクションメタデータの分離を改善しました。また、特に ScalarDB Cluster および ScalarDB SQL における BLOB 値に関するいくつかのデータ正確性の問題に対処し、SQL の解析と検証を改善しました。さらに、スキーマ管理を強化し、さまざまなストレージアダプターの問題を修正し、依存関係のアップグレードと脆弱性の修正によりセキュリティを強化しました。

### Community edition

#### 改善点

- 仮想テーブルの一貫した読み取りに ScalarDB が必要とする分離レベルを、Oracle、PostgreSQL、AlloyDB、YugabyteDB、MySQL、MariaDB、および TiDB で READ COMMITTED に引き下げました。この変更により、これらのデータベースで、Oracle と PostgreSQL のデフォルトの分離レベルである READ COMMITTED でトランザクションメタデータの分離を使用できるようになり、Oracle で SERIALIZABLE が不要になりました。 ([#4148](https://github.com/scalar-labs/scalardb/pull/4148))
- Schema Loader の `--repair-all` で、`--coordinator` または `--replication-tables` が指定されている場合にスキーマファイルを省略できるようにし、テーブルスキーマを再適用せずに Coordinator テーブルとレプリケーションテーブルを修復できるようにしました。また、スキーマファイル、`--coordinator`、`--replication-tables` のいずれも指定せずに `--repair-all` を実行した場合、エラーで失敗する代わりに、何も行わずに正常終了するようになりました。 ([#4183](https://github.com/scalar-labs/scalardb/pull/4183))

#### バグの修正

- 主キーの値のみを指定した条件付き put (`PutIfExists` または `PutIf`) が、JDBC データベースで SQL エラーにより失敗する問題を修正しました。Spanner では、主キー列のみを持つテーブルに対するこのような put は引き続き失敗します。 ([#4129](https://github.com/scalar-labs/scalardb/pull/4129))
- JDBC データベースで、トランザクションメタデータの分離を使用してインポートされたテーブルの問題を修正しました。インポート以降にどのトランザクションも書き込んでいないレコードが、それを書き込んだトランザクションがロールバックされた後に、更新または削除できなくなる問題がありました。また、最初のトランザクションが読み取った後に別のトランザクションが削除したレコードを、最初のトランザクションが再作成できる問題もありました。Spanner では、主キー列のみを持つテーブルで後者が引き続き発生します。この問題によりすでに更新または削除できなくなっているレコードは、アップグレード後もその状態のままです。それらを復旧するには、すべてのアプリケーションをアップグレードした後、インポートされたテーブルの `<table_name>_tx_metadata` テーブルから、`tx_id` 列が `NULL` であるレコードを削除してください。たとえば、`DELETE FROM <namespace>.<table_name>_tx_metadata WHERE tx_id IS NULL` のように実行します。 ([#4131](https://github.com/scalar-labs/scalardb/pull/4131))
- JDBC データベースで、トランザクションメタデータの分離を使用してインポートされたテーブルにおいて、ワンフェーズコミットが有効な場合に、インポート以降にどのトランザクションも書き込んでいないレコードの削除が `IllegalArgumentException` で失敗する問題を修正しました。 ([#4133](https://github.com/scalar-labs/scalardb/pull/4133))
- ScalarDB Schema Loader および ScalarDB Data Loader CLI コンテナイメージで、ベースイメージを Eclipse Temurin 21.0.13_9 に更新することで、[CVE-2026-91403](https://github.com/advisories/GHSA-9h75-rf66-wh3r "CVE-2026-91403") および [CVE-2026-114820](https://github.com/advisories/GHSA-255q-pwv4-fjj7 "CVE-2026-114820") (eMudhra CA の侵害) を修正しました。このベースイメージは、侵害された emSign ルート CA を信頼しなくなりました。 ([#4143](https://github.com/scalar-labs/scalardb/pull/4143))
- Guava ライブラリをアップグレードしてセキュリティ問題を修正しました: [CVE-2026-102554](https://github.com/advisories/GHSA-xxph-c9ww-hj94 "CVE-2026-102554") ([#4144](https://github.com/scalar-labs/scalardb/pull/4144))
- ScalarDB をライブラリとして使用するアプリケーションは、Netty および Jackson のバージョンを自身で管理していない限り、修正済みのバージョンを取得するようになりました。以前は、これらのライブラリの脆弱性の修正 (たとえば、Netty の [CVE-2026-75595](https://github.com/advisories/GHSA-c4c3-7fpv-j4q5 "CVE-2026-75595")、Jackson の [CVE-2026-89407](https://github.com/advisories/GHSA-p6pp-m3f8-5c89 "CVE-2026-89407")、[CVE-2026-89425](https://github.com/advisories/GHSA-7hhh-6rmp-j9qf "CVE-2026-89425")、[CVE-2026-68497](https://github.com/advisories/GHSA-q4xh-88c3-wmh7 "CVE-2026-68497")、[CVE-2026-91776](https://github.com/advisories/GHSA-wv8q-qhhj-9h54 "CVE-2026-91776")、および [CVE-2026-91777](https://github.com/advisories/GHSA-cxp5-3px4-pw24 "CVE-2026-91777")) は、ScalarDB 自身のビルドとコンテナイメージにのみ適用されていました。その結果、これらのアプリケーションの Jackson は 2.22 にアップグレードされます。ScalarDB のバージョンによっては、Maven でビルドされたアプリケーションは、以前は `jackson-databind` 2.7 や Netty 4.1.94 など、はるかに古いバージョンを取得していました。このリリースでは、Netty の [CVE-2026-73508](https://github.com/advisories/GHSA-mfg7-5gfp-c4w3 "CVE-2026-73508") も修正しました。この脆弱性は、これらのアプリケーションだけでなく、Schema Loader および Data Loader CLI イメージにも影響していました。 ([#4146](https://github.com/scalar-labs/scalardb/pull/4146))
- Amazon S3 を使用した Object Storage アダプターで、複数のテーブルを同時に切り詰めまたは削除すると、無期限にハングする可能性がある問題を修正しました。 ([#4149](https://github.com/scalar-labs/scalardb/pull/4149))
- Oracle、MySQL、MariaDB、または TiDB からテーブルをインポートする際に、主キー列がテーブルの主キーの順序ではなく、列名のアルファベット順で登録される問題を修正しました。この修正後にインポートされたテーブルでは、Data Loader のエクスポートの `--partition-key` を含め、テーブルの主キーの順序でキーを指定してください。この修正前にインポートされたテーブルは、既存の順序のままです。 ([#4175](https://github.com/scalar-labs/scalardb/pull/4175))
- [CVE-2026-40983](https://github.com/advisories/GHSA-w737-wx49-qj23 "CVE-2026-40983") および [CVE-2026-40984](https://github.com/advisories/GHSA-g3pr-3p32-fp23 "CVE-2026-40984") を修正するために、Micrometer (`micrometer-core`、`micrometer-observation`、および `micrometer-commons`) を 1.15.12 にアップグレードしました。ScalarDB はこれらを直接宣言し、これらを取り込むライブラリから除外するようになったため、ScalarDB をライブラリとして使用するアプリケーションも、Micrometer のバージョンを自身で管理していない限り、修正済みのバージョンを取得します。 ([#4192](https://github.com/scalar-labs/scalardb/pull/4192))

### Enterprise edition

#### バグの修正

##### ScalarDB Cluster

- 埋め込みクライアントが、`ContainsString` などのサポートされていないフィルタータイプに対して、`UnsupportedOperationException` ではなく `AssertionError` をスローする問題を修正しました。
- すべての ScalarDB Cluster コンテナイメージで、ベースイメージを Eclipse Temurin 21.0.13_9 に、また UBI ベースのノードイメージでは `java-21-openjdk` 21.0.13.0.9 に更新することで、[CVE-2026-91403](https://github.com/advisories/GHSA-9h75-rf66-wh3r "CVE-2026-91403") および [CVE-2026-114820](https://github.com/advisories/GHSA-255q-pwv4-fjj7 "CVE-2026-114820") (eMudhra CA の侵害) を修正しました。これらのベースイメージは、侵害された emSign ルート CA を信頼しなくなりました。
- grpc_health_probe バイナリをアップグレードしてセキュリティ問題を修正しました: [CVE-2026-116587](https://github.com/advisories/GHSA-mgcc-cww5-fp2q "CVE-2026-116587")
- Guava ライブラリをアップグレードしてセキュリティ問題を修正しました: [CVE-2026-102554](https://github.com/advisories/GHSA-xxph-c9ww-hj94 "CVE-2026-102554")
- ScalarDB Cluster クライアントが、`ByteBuffer` としてバインドされた BLOB 値を送信するたびにバッファの末尾まで読み取っていたため、2回目以降 (ステートメントが再実行または再試行される場合、同じバッファが複数のバインドマーカーにバインドされている場合、バッチ内のステートメントが同じ値を共有している場合など) は、値が空の BLOB として送信されるバグを修正しました。その結果、エラーなしで空の BLOB が書き込まれたり、BLOB 列が空の BLOB と比較されたりする可能性がありました。クライアントは、バッファの位置を変更せずにバイトをコピーするようになりました。この修正では、すでに影響を受けたデータは修復されません。
- 書き込みバッファリングが有効な場合に、ScalarDB Cluster クライアントが、バッファリングされた `INSERT` および `UPSERT` ステートメントを、実行時の値ではなく、バッファリングされたステートメントの送信時の値で送信するバグを修正しました。アプリケーションがステートメントの実行後に `BoundStatement` や、BLOB 値のバイト配列または `ByteBuffer` を再利用した場合、それを使用するバッファリングされたすべてのステートメントが最後の値で送信され、エラーなしで誤った値の行が書き込まれる可能性がありました。クライアントは、ステートメントをバッファリングするときに、その値をコピーするようになりました。この修正では、すでに影響を受けたデータは修復されません。
- [CVE-2025-14813](https://github.com/advisories/GHSA-574f-3g2m-x479 "CVE-2025-14813")、[CVE-2026-0636](https://github.com/advisories/GHSA-c3fc-8qff-9hwx "CVE-2026-0636")、[CVE-2026-5588](https://github.com/advisories/GHSA-wg6q-6289-32hp "CVE-2026-5588")、[CVE-2026-5598](https://github.com/advisories/GHSA-p93r-85wp-75v3 "CVE-2026-5598")、[CVE-2026-8763](https://github.com/advisories/GHSA-9pwp-9qqc-pr26 "CVE-2026-8763")、および [CVE-2026-13506](https://github.com/advisories/GHSA-qp49-qgx5-5m26 "CVE-2026-13506") を修正するために、Java クライアント SDK および埋め込み Java クライアント SDK で Bouncy Castle (`bcprov-jdk18on`、`bcpkix-jdk18on`、および `bcutil-jdk18on`) を 1.86 にアップグレードしました。これらの SDK を使用するアプリケーションは、Bouncy Castle のバージョンを自身で管理していない限り、修正済みのバージョンを取得するようになりました。以前は、修正済みのバージョンは、ScalarDB Cluster 自身のビルドと BYOL 以外のコンテナイメージにのみ適用されており、BYOL コンテナイメージでは、依存関係が取り込んだ Bouncy Castle 1.70 のクラスが読み込まれていました。BYOL コンテナイメージも、修正済みのバージョンを使用するようになりました。
- Java クライアント SDK または埋め込み Java クライアント SDK を使用して Maven でビルドするアプリケーションは、すべての Jackson アーティファクトで同じバージョンを取得するようになりました。以前は、`jackson-dataformat-cbor` など、一部のアーティファクトが、SDK の他の依存関係が要求する古いバージョンになる可能性がありました。埋め込み Java クライアント SDK は、Jackson をコンパイル時の依存関係として公開しなくなりました。アプリケーションが Jackson を直接使用し、SDK による提供に依存していた場合は、アプリケーションのビルドで Jackson を宣言してください。

##### ScalarDB GraphQL

- Guava ライブラリをアップグレードしてセキュリティ問題を修正しました: [CVE-2026-102554](https://github.com/advisories/GHSA-xxph-c9ww-hj94 "CVE-2026-102554")

##### ScalarDB SQL

- Guava ライブラリをアップグレードしてセキュリティ問題を修正しました: [CVE-2026-102554](https://github.com/advisories/GHSA-xxph-c9ww-hj94 "CVE-2026-102554")
- `byte[]` から作成された BLOB 値の `Value.hashCode()` を、`equals()` と一貫性を持つように修正しました。この不整合により、主キーまたはインデックス付き列に対する同じ BLOB の等価条件をすべての `OR` グループで繰り返す `SELECT`、`UPDATE`、または `DELETE` ステートメントが、効率の悪いスキャンで計画されたり、クロスパーティションスキャンのフィルタリングが有効でない限り失敗するクロスパーティションスキャンとして計画されたりする可能性がありました。
- 誤った BLOB 値が暗黙的に書き込まれたり比較されたりする可能性がある 2 つのバグを修正しました。ダイレクトモードでは、`BoundStatement.setBlob()`、`Value.ofBlob()`、`Value.of()`、または JDBC の `setObject()` メソッドを通じて `ByteBuffer` としてバインドされた BLOB 値が、使用されるたびにバッファの末尾まで読み取られていたため、複数の行を更新する `UPDATE` ステートメントや再実行されたステートメントが、空の BLOB を書き込んだり、BLOB 列を空の BLOB と比較したりしていました。JDBC ドライバーでは、`setBytes()` および `setObject()` がアプリケーションの配列またはバッファへの参照を保持していたため、バッチの各行で 1 つの配列またはバッファを再利用すると、すべての行に最後の内容が書き込まれていました。ScalarDB SQL は、これらの値を使用するときに、アプリケーションのバッファや配列を読み取る代わりにコピーするようになりました。この修正では、すでに影響を受けたデータは修復されません。
- SQL パーサーが一部の SQL を誤って解釈するバグを修正しました。読み取れない文字を破棄していたため、`INSERT INTO ns.té` がテーブル `ns.t` に対して実行され、バッククォートや角括弧で囲まれた名前が受け入れられていました。また、`5AND` のように、数値の後に空白なしで単語が続く場合に、数値と単語として読み取り、終了していないブロックコメントをステートメントの残りの部分とともに無視していました。ScalarDB Cluster では、このような SQL により、トランザクション外のステートメントが、`WITH` 句の認証情報ではなく、クライアント設定の認証情報で実行される可能性がありました。このような SQL は、構文エラーとして拒否されるようになり、`--` は、SQL 標準と同様に、後に何が続いても行コメントを開始するようになりました。コメント `/*!*/` は、次の `*/` までの SQL をパーサーがスキップすることがなくなりました。これにより、`DELETE` ステートメントがすべての行を削除する可能性がありました。
- `GROUP BY` 句も集計関数もない `SELECT` ステートメントの `HAVING` 句が暗黙的に無視され、`WHERE` 句に一致するすべての行がステートメントによって返される問題を修正しました。SQL 標準と同様に、`HAVING` 句のみを指定するとすべての行が 1 つのグループになるため、このようなステートメントは、`GROUP BY` 句にも集計関数にも含まれない列を選択する他のステートメントと同じエラーで拒否されるようになりました。そのため、以前は行を返していたステートメントが失敗する可能性があります。行をフィルタリングするには、条件を `WHERE` 句に移動してください。`GROUP BY` 句または集計関数を持つステートメントは影響を受けません。また、そのような列に対するエラーメッセージは、内部の詳細ではなく、記述されたとおりの列を表示するようになりました。

## v3.18.3

**発売日:** 2026年10月30日

### まとめ

このリリースでは、SQL Server 2025 のサポートを追加し、SQL Server 2017 のサポートを終了しました。また、Consensus Commit におけるトランザクションの信頼性とエラー処理を改善し、テーブルメタデータ操作を最適化し、ストレージアダプター操作の正確性と信頼性を向上させ、リソース管理を改善しました。さらに、認証および認可の修正、依存関係のアップグレード、脆弱性の緩和によりセキュリティを強化し、ScalarDB SQL におけるデータの比較と集計の問題に対処しました。

### Community edition

#### 改善点

- JDBC データベースでの単一の put または delete 操作におけるロック待機タイムアウトやシリアライズ失敗などの競合エラーが、再試行可能として分類されない問題を修正しました。その結果、Consensus Commit は、コミット中のそのような競合を `CommitException` または `UnknownTransactionStatusException` ではなく `CommitConflictException` として報告できるようになりました。 ([#3852](https://github.com/scalar-labs/scalardb/pull/3852))
- Consensus Commit のレコードリカバリが、基盤となるストレージによって報告された競合エラーを再試行し、解消されない競合を競合として報告して、トランザクションを再試行できるように修正しました。 ([#3853](https://github.com/scalar-labs/scalardb/pull/3853))
- テーブルが存在するかどうかを確認する処理のパフォーマンスを改善しました。`tableExists()` は、ネームスペース内のテーブルを一覧表示する代わりに、指定されたテーブルのメタデータのみを読み取るようになったため、そのコストはテーブル数に応じて増加しなくなりました。その結果、DynamoDB では、ScalarDB のメタデータを持たないテーブルは存在するものとして報告されなくなりました。また、ScalarDB のメタデータテーブルまたはコンテナーが存在しない場合に、DynamoDB および Cosmos DB の `getTableMetadata()` が `null` を返す代わりに例外をスローする問題も修正しました。そのため、これらのストレージでは、「テーブルが見つかりません」というエラーは、メタデータテーブルまたはコンテナー自体が存在しないことを意味する場合もあります。そのようなテーブルが AWS コンソールまたは Azure ポータルで確認できる場合は、`repairTable()` を実行する前に、すべての設定間で `scalar.db.system_namespace_name` (および DynamoDB の場合はネームスペースプレフィックス) が一致していることを確認してください。 ([#3947](https://github.com/scalar-labs/scalardb/pull/3947))
- SQL Server 2025 のサポートを追加し、SQL Server 2017 のサポートを終了しました。 ([#3998](https://github.com/scalar-labs/scalardb/pull/3998))
- テーブルのインポートで、TEXT の照合順序に従えない列タイプ(SQL Server の `nchar`、`nvarchar`、`text`、`ntext`、Oracle の `NCHAR` および `NVARCHAR2`、Db2 の `GRAPHIC`、`VARGRAPHIC`、`DBCLOB`)を拒否するように変更しました。 ([#4051](https://github.com/scalar-labs/scalardb/pull/4051))
- SQL Server JDBC ドライバーを 13.6.0 にアップグレードし、1582年10月15日より前の日付の TIMESTAMPTZ 値が SQL Server に最大10日ずれて保存される問題を修正しました。以前のバージョンの ScalarDB によって SQL Server に保存された、1582年10月15日より前の日付の TIMESTAMPTZ 値は、書き込まれた値より最大10日前の値として読み取られます。そのようなデータがある場合は、ずれを解消するためにデータの移行を検討してください。 ([#3971](https://github.com/scalar-labs/scalardb/pull/3971))
- S3 および Cloud Storage アダプターを改善し、テーブルの切り詰めまたは削除時に、一時的なエラーで失敗したオブジェクトの削除を再試行するようにしました。 ([#4077](https://github.com/scalar-labs/scalardb/pull/4077))

### まとめ

このリリースには、多くの改善点、セキュリティ問題の修正、およびバグ修正が含まれています。

:::warning 破壊的変更

- **JDBC コネクションプールが Apache Commons DBCP2 から HikariCP に移行しました:**
  - 次の設定プロパティはサポートされなくなりました。設定されている場合は警告がログに記録されて無視されます:
    - `scalar.db.jdbc.connection_pool.max_idle`
    - `scalar.db.jdbc.table_metadata.connection_pool.max_idle`
    - `scalar.db.jdbc.admin.connection_pool.max_idle`
    - `scalar.db.jdbc.prepared_statements_pool.enabled`
    - `scalar.db.jdbc.prepared_statements_pool.max_open`
  - プリペアドステートメントプーリングは HikariCP には同等の機能がないため、利用できなくなりました。
  - コネクションプールのデフォルト動作は DBCP2 ではなく HikariCP に従います。これにより、設定変更がなくても実行時の動作が変わる可能性があります (例: コネクション取得タイムアウトとアイドルエビクション)。
- **既存のテーブルは、新しい before-image セカンダリインデックスを作成するために `repairTable()` が必要です。** Consensus Commit のインデックスベースの `Get`、`Scan`、`ScanAll` 操作は、コンパニオンの `before_<col>` インデックスに依存するようになりました。既存のテーブルそれぞれで `repairTable()` を実行するまで、ScalarDB はスタートアップ時に警告をログに出力し、インデックスベースの読み取りは以前の動作にフォールバックします。これにより、インデックス列が同時に更新されているレコードを見落とす可能性があります。設定 `scalar.db.consensus_commit.index.eventually_consistent_read.enabled` はオプトアウト用に提供されていますが、新しいワークロードにはお勧めしません。
- **MySQL Connector/J が MariaDB Connector/J に置き換わりました。** SSL はデフォルトで有効になりません。MySQL 8.0 以降に `caching_sha2_password` 認証で接続する場合は、JDBC URL に `sslMode=REQUIRED` または `allowPublicKeyRetrieval=true` を追加してください。`jdbc:mysql://` URL の場合、ScalarDB が互換性のために自動的に `permitMysqlScheme` を追加するため、操作は不要です。
- **`BigIntColumn.MAX_VALUE` および `BigIntColumn.MIN_VALUE` 定数が削除されました。** これらを参照していたコードは、代わりに `Long.MAX_VALUE` および `Long.MIN_VALUE` を使用する必要があります。

:::

#### 改善点

##### ScalarDB Cluster

- 内部認証トークン処理をリファクタリングし、文字列プレフィックス解析の代わりに型安全なクラス階層を使用するようにしました。
- Auth、ABAC、Encryption モジュールは、グローバルに `scalar.db.cross_partition_scan.enabled=true` を有効にする必要がなくなりました。これらのモジュールは操作レベルのクロスパーティションスキャン属性を使用し、Snapshot Isolation で内部メタデータトランザクションを実行するようになりました。
- 非推奨ポリシーを変更し、非推奨のマーク付けされた API は 5.0.0 ではなく 4.0.0 で削除されるようになりました。

##### ScalarDB GraphQL

- GraphQL `BigInt` スカラーが受け入れる値の範囲を緩和し、完全な Java `long` 範囲にしました。バックエンド固有の制限 (Cosmos DB とオブジェクトストレージは引き続き BigInt を `-2^53` から `2^53` に制限) は、GraphQL レイヤーではなく ScalarDB ストレージレイヤーで適用されるようになりました。

##### ScalarDB SQL

- 二段階コミットインターフェーストランザクション内のスレッドプール管理を改善し、Spring Data JDBC for ScalarDB での潜在的なスターベーション問題を回避しました。
- ワンショットクエリ実行用のワン操作モードサポートを追加し、SQL クエリを単一操作として表現できる場合は明示的なトランザクション begin/commit をスキップしてパフォーマンスを向上させました。
- TIME (マイクロ秒精度)、TIMESTAMP (ミリ秒精度)、TIMESTAMPTZ (ミリ秒精度) 列の値を挿入または更新する際、範囲外の精度は例外をスローするのではなく切り捨てられるようになりました。
- CLI モジュール用の shadow jar が不必要に GitHub Packages に公開される問題を修正しました。
- TIMESTAMPTZ リテラルを更新し、UTC タイムゾーン `Z` 文字の前のスペース文字をオプションにしました。例えば、`2021-03-04 12:30:45.123Z` が現在の形式 `2021-03-04 12:30:45.123 Z` に加えて受け入れられるようになりました。また、TIMESTAMPTZ 列を選択する際、値は `Z` の前にスペースを入れずに表示されます。
- SQL ステートメントビルダー API をリファクタリングし、型安全性とエルゴノミクスを改善しました。`SelectStatementBuilder` は SQL 句の順序を型レベルで強制するようになり、`having()` は `groupBy()` の後にのみ呼び出し可能になります。また HAVING は WHERE と同じ流暢な `.and(...)` / `.or(...)` チェーンをサポートします。`Having.of(...)` ファクトリーが `Having.create(...)` に統合されました。`CreateUserStatementBuilder` / `AlterUserStatementBuilder` は、前述のオーバーロードされた `with(...)` に代わって、明示的な `withPassword()` / `withSuperuser()` / `withNoSuperuser()` メソッドが公開されます。`UserOption` 列挙型が削除され、`CreateUserStatement` / `AlterUserStatement` の nullable `superuser` ブール値に置き換わりました。`FunctionRef` は一般的な集計用の便利なファクトリー (`count()`、`sum(...)`、`avg(...)`、`min(...)`、`max(...)`) を提供するようになりました。

#### バグの修正

##### ScalarDB Cluster

- `GRANT ROLE` コマンドをべき等にしました。重複する付与を許可し、再付与時に `WITH ADMIN OPTION` にアップグレードされるようになりました。
- `scalar-metering` をアップグレードして、ScalarDB Cluster が Omnistrate 環境にデプロイされない問題を修正しました。
- トランザクションの有効期限が切れた場合に一時停止機能が正しく機能しなかったバグを修正しました。
- piggyback commit を使用したバッチ操作が、コミット競合が発生した場合に `CrudException` の代わりに `CrudConflictException` をスローする問題を修正しました。これにより、クライアントがコミット競合を適切に検出して処理できるようになります。
- piggyback commit を使用した `batch()` が予期しない gRPC エラーで `CrudException` の代わりに `UnknownTransactionStatusException` をスローするバグを修正しました。piggyback commit が有効な場合、トランザクションステータスが実際には不明であるにもかかわらず、これがクライアント側で誤ったエラー処理を引き起こす可能性がありました。

##### ScalarDB SQL

- ORDER BY および HAVING 句で曖昧な列名が検出されました。
- `StatementUtils.appendTerm()` で `DATE`、`TIME`、`TIMESTAMP`、および `TIMESTAMPTZ` の値を処理する際に発生していた `ClassCastException` を修正しました。これらの値は、String に誤ってキャストされるのではなく、文字列リテラルとして正しくフォーマットされるようになりました。
- `SelectStatement.toSql()` を修正し、`SUM()` および `COUNT()` などの集計関数を使用した ORDER BY 句を正しく生成するようにしました。以前は列ベースの順序付けのみが処理され、関数ベースの順序付けが使用される場合に不正な SQL 出力が生成されていました。
- CREATE TABLE ステートメントで重複する列名が許可されるバグを修正しました。
- 時間関連の型フォーマッターで厳密な日付検証が欠落していた問題を修正しました。これにより、無効な日付 (例: 2月30日) が拒否されずに静かに受け入れられる可能性がありました。
- `ResultSet.getObject` は BLOB 列で `java.sql.Blob` を返すようになり、`ResultSet.getBlob`、`ResultSet.getBinaryStream`、および複数の `PreparedStatement.setBlob` / `setBinaryStream` オーバーロードがサポートされるようになりました。`ResultSetMetaData.getColumnType` は FLOAT 列で `Types.REAL` (以前は `Types.FLOAT`) を返すようになりました。`ResultSet.getString` は JDBC 仕様に準拠して、SQL NULL に対してリテラル文字列 `"null"` ではなく Java `null` を返すようになりました。付随的な効果として、SQL CLI は BLOB 値を `[B@xxxxxxxx` ではなく `X'...'` 16進リテラルとしてレンダリングします。
- `CachedMetadata#invalidateNamespaceNamesCache()` が実際に名前空間のキャッシュリストを無効にしなかった問題を修正しました。これにより `SHOW NAMESPACES` および関連操作がキャッシュ TTL が期限切れになるまで古い結果を返す可能性がありました。
